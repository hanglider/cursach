# ADR 0006. Начальные веса 0.5 / 0.3 / 0.2 и офлайн sensitivity-анализ

Дата: 2026-09-13. Закрывает spec 8.3 (часть про веса), open-questions 2.1 п. 2–3.

## Статус

Принят.

## Контекст

Веса `w1, w2, w3` заявлены как настраиваемые, но способ их выбора не был
определён. Подбор по сетке с повторными chaos-прогонами стоил бы часы на
точку. Sensitivity-анализ назван возможным самостоятельным результатом.

## Решение

1. **Начальные веса** `w1 = 0.5, w2 = 0.3, w3 = 0.2` (error rate, latency,
   saturation). Error rate доминирует: он ближе всего к пользовательскому
   опыту отказа. Флаг `--weights=0.5,0.3,0.2`.
2. **Веса предрегистрированы.** Целевой показатель «error rate ниже наивного
   на ≥ 20%» оценивается только с этими весами. Подгонять веса под лучший
   результат после прогонов нельзя.
3. **Каждое решение хранит параметры scoring** — поле
   `placement_decisions.scoring JSONB`: `{"weights": [..],
   "latency_budget_ms": 200, "formula": "adr-0005"}`. Дополняет схему ADR 0004.
4. **Sensitivity-анализ офлайн** (задача 9): по `placement_decisions`
   (все кандидаты со снимком метрик, ADR 0004) решения пересчитываются на
   сетке весов (симплекс с шагом 0.1). Результат: доля решений, в которых
   argmax меняется относительно базовых весов, и для прогонов сценария 2 —
   расчётная доля размещений в деградировавший кластер при каждой точке
   сетки. Без повторных chaos-прогонов.

## Последствия

Плюсы:

- Честная методика: числа для приёмки считаются с заранее объявленными
  весами, а зависимость от весов — отдельный результат.
- Sensitivity стоит секунды, а не часы.

Минусы:

- Офлайн-пересчёт предполагает, что иное решение не изменило бы метрики
  кластеров. Это не совсем так: размещение в деградировавший кластер
  добавляет ему нагрузки. При 50 RPS и шести живых workload'ах эффект мал;
  ограничение фиксируется в отчёте.
- Начальные веса — экспертное суждение, не результат обучения. Именно
  поэтому sensitivity-анализ обязателен, а не желателен.
