# ADR 0007. Пороги, гистерезис, определение недоступности и TTD

Дата: 2026-09-13. Закрывает spec 8.4, open-questions 2.2.

## Статус

Принят.

## Контекст

spec §4.6 объявляет инцидент при «error rate выше порога или недоступности
дольше T секунд», не задавая ни порога, ни T, ни защиты от флаппинга.
architecture §6.2 предлагал асимметричные переходы. Дополнительно требовалось
определить, что значит «недоступен», и в какой момент фиксируется TTD.

Существенное ограничение, выявленное при решении 2.5 (ADR 0023): базовый
отказ сценария 1 — PodChaos — не трогает API-сервер. Правило «недоступен,
когда не отвечают и API, и сервис» никогда не дало бы DOWN.

## Решение

**Период опроса** DR Controller'а — 10 с. За цикл по каждому кластеру
собираются три сигнала:

| Сигнал | Источник | Порог |
|---|---|---|
| `svc_ok` | `GET /healthz` долгоживущего `app` кластера по адресу узла и NodePort 31998 (ADR 0011), таймаут 2 с | ответ 200 |
| `api_ok` | `GET {api_endpoint}/readyz`, без аутентификации, таймаут 2 с | ответ 200 |
| `sli_ok` | `cluster:http_error_rate:ratio1m` из Thanos Querier | ≤ 0.05 |

Окно error rate для DR — **1 минута**: обнаружение требует скорости. Каталог
для scoring использует окно 5 минут (architecture §2.4): размещение требует
стабильности. Разные окна намеренны.

**Недоступность** определяется только пробой сервиса: `svc_ok = false`.
Проба API вспомогательная: её падение при живом сервисе — DEGRADED и запись
в лог, но не failover. Обоснование: SLO измеряет доступность сервиса для
пользователя, а Kubernetes продолжает обслуживать трафик при отказе control
plane.

**Переходы:**

| Переход | Условие |
|---|---|
| HEALTHY → DEGRADED | 1 цикл: `!sli_ok` или `!svc_ok` или `!api_ok` |
| DEGRADED → HEALTHY | 3 цикла подряд все сигналы в норме |
| DEGRADED → DOWN | `!svc_ok` 3 цикла подряд (T = 30 с). Error rate сам по себе в DOWN не ведёт |
| DOWN → RECOVERING | `svc_ok` 1 цикл **и** smoke-тест: 10 запросов к `app` кластера, все 200 |
| RECOVERING → HEALTHY | вес трафика возвращён ступенями 10% → 50% → 100% от номинала (ADR 0011), каждая ступень удерживается 2 чистых цикла; итого не менее 6 циклов |
| RECOVERING → DOWN | `!svc_ok` 3 цикла подряд; вес снова 0 |

Грязный цикл в RECOVERING (`!sli_ok` при живой пробе) не откатывает вес, а
обнуляет счётчик чистых циклов на текущей ступени.

**Действия:**

- На DOWN: вес отказавшего кластера на маршруте `app.fed.local` → 0
  (ADR 0011, 0017); `PATCH /clusters/{id}/status` → `down` (ADR 0003).
- На RECOVERING: `down` в каталоге снимается сразу — сервис кластера
  работает, размещать туда снова можно; трафик возвращается ступенями.

**Измерение:**

- `TTD = detected_at − fault_injected_at`, где `detected_at` — переход в
  DEGRADED. Ожидаемо 10–20 с.
- Failover только на DOWN. `RTO = failover_completed_at − fault_injected_at`,
  где `failover_completed_at` — момент успешного PATCH HTTPRoute. Ожидаемо
  40–50 с.
- В сценарии 2 (деградация сети) DOWN не наступает: сервис отвечает, пусть
  медленно и с ошибками. Трафик не переключается, реагирует только
  планировщик через каталог. Это намеренно: иначе эффект планировщика
  смешался бы с эффектом DR. Уточнено ADR 0031: «DOWN не наступает» —
  предположение, поэтому сценарий 2 гоняется с DR в режиме `observe`, а
  `peak_state` инцидентов пишется в сводку прогона.

## Последствия

Плюсы:

- Быстрое признание деградации (TTD < 60 с с запасом) и медленное
  восстановление: возврат трафика в нестабилизировавшийся кластер стоит
  дороже лишней минуты на резерве.
- Отказ control plane при живом сервисе не вызывает failover; это правильное
  поведение для Kubernetes.

Минусы:

- DOWN раньше чем через 30 с недостижим; RTO не может быть меньше ~40 с.
  Для порога 5 минут это несущественно.
- Проба сервиса смотрит на один Deployment (`app`). Его собственная поломка
  при здоровом кластере выглядит как отказ кластера. Смягчение: `app` с двумя
  репликами; и `app` — тот самый сервис, чей SLO измеряется, так что его
  отказ и есть отказ с точки зрения пользователя.
- DR Controller держит собственное состояние DEGRADED, не совпадающее с
  `degraded` каталога (тот считается по метрикам). Оба используют порог
  0.05, поэтому по error rate они совпадают; по пробам — нет. В отчёте
  оговаривается.
- DR читает Thanos напрямую (spec §4.6, architecture §1.1), в отличие от
  планировщика; инвариант 2 касается только планировщика.
