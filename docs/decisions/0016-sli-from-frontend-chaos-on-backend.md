# ADR 0016. Точка измерения SLI: серверные метрики frontend'а, отказ вносится в backend

Дата: 2026-09-13. Закрывает open-questions 1.4.

## Статус

Принят.

## Контекст

Каталог берёт error rate и p95 из Prometheus кластера через Thanos, то есть из
серверных метрик сервиса. Сценарий 2 вносит задержку 500 мс и потери 10% на
сети одного кластера. Сервис измеряет длительность от получения запроса до
ответа; сетевая задержка снаружи в неё не попадает. Если chaos применить к
самому сервису «снаружи», серверные метрики останутся здоровыми, каталог не
увидит деградации, планировщик не отреагирует, и эксперимент ничего не
покажет.

Отклонённые варианты: per-upstream метрики шлюза как источник для каталога
(Thanos-агрегация in-cluster Prometheus теряет роль); синтетические пробы
blackbox exporter'ом (не SLO реального трафика).

## Решение

1. **Источник SLI для каталога** — серверные метрики frontend'а из in-cluster
   Prometheus через Thanos Querier, как в spec §4.2–4.3. Запросы —
   architecture §2.4 с фильтром `tier="frontend"`.
2. **Точка внесения отказа в сценарии 2** — поды `backend` целевого кластера
   (Chaos Mesh NetworkChaos по селектору `app.kubernetes.io/component=backend`).
   frontend видит медленные и упавшие вызовы backend'а и отражает их в своих
   метриках: длительность растёт, таймауты дают `502`.
3. **Клиентский ряд** k6 (error rate, латентность через шлюз) пишется в
   результаты как второй ряд для сверки, но каталог его не читает.

## Последствия

Плюсы:

- Спецификация не меняется: каталог читает то, что задано.
- Один и тот же отказ виден и серверу, и клиенту; расхождение рядов — само по
  себе результат (например, доля ошибок, которые видит клиент, но не сервер).

Минусы:

- Деградация на участке шлюз → кластер (например, chaos на frontend'е или на
  сети между control и федерацией) каталогу не видна: сервис измеряет только
  то, что происходит за ним. Для сценария 1 это закрывается пробами
  DR-контроллера (открытый вопрос 2.2), для сценария 2 — выбором точки
  внесения отказа. Ограничение фиксируется в отчёте.
- Показания зависят от таймаута frontend → backend (ADR 0014): при задержке
  500 мс и таймауте 1 с большинство запросов станут медленными, но не
  ошибочными; ошибки дадут потери пакетов и ретрансмиты. Ожидаемая картина
  сценария 2 — рост p95 сильнее роста error rate; целевой показатель «error
  rate ≥ 20% ниже наивного» оценивается на этом фоне.
