# ADR 0008. Нагрузка: k6, постоянные 50 RPS, структура прогона, три повтора

Дата: 2026-09-13. Закрывает spec 8.8 (часть про нагрузку), open-questions 1.2.

## Статус

Принят.

## Контекст

Целевые показатели spec §1.3 (availability ≥ 99.0%, p95 < 200 мс) заданы
«при нормальной нагрузке», которая не была определена. Без зафиксированного
профиля и структуры прогона сравнение «до/после» невоспроизводимо.

## Решение

1. **Генератор** — k6, сценарии в `experiments/load/`. Запускается на
   хост-машине (установлен через brew), то есть вне федерации (ADR 0001).
2. **Профиль** — постоянные 50 RPS, executor `constant-arrival-rate`, без
   ramp-up. Постоянная нагрузка исключает второй источник изменения метрик
   при сравнении.
3. **Клиентские метрики** k6 пишет через Prometheus remote write в
   Prometheus control-кластера (`--web.enable-remote-write-receiver`), рядом
   с которым стоит Thanos sidecar, так что клиентский и серверный взгляд
   доступны из одного Querier'а и попадают в один экспорт (ADR 0002).
4. **Структура прогона:** 3 мин baseline → внесение отказа → 5 мин под
   отказом → снятие отказа → 5 мин восстановления. Около 13 минут.
5. **Повторы:** 3 прогона на каждую конфигурацию (сценарий × планировщик,
   сценарий × с DR / без DR). В отчёт — среднее и разброс.
6. Каждый прогон получает `run-id`; параметры (сценарий, планировщик,
   структура, версия сценариев k6, параметры потока workload'ов из ADR 0015)
   пишутся в `experiments/results/<run-id>/meta.json` вместе с экспортом.

## Последствия

Плюсы:

- «Нормальная нагрузка» и «штатный режим» стали воспроизводимым файлом в
  репозитории.
- k6 даёт клиентский error rate и латентность бесплатно — второй ряд к
  серверным SLI (ADR 0016).

Минусы:

- Время: 13 мин × 3 повтора × число конфигураций. Три сценария × две
  конфигурации — около 4 часов чистого прогона без учёта подготовки.
- 50 RPS — скромная нагрузка: saturation в scoring-функции при ней почти не
  меняется, и её вклад в решения планировщика на стенде будет мал. Это
  ограничение стенда, а не формулы; фиксируется в отчёте.
- Путь k6 → шлюз проходит через сеть хоста и docker-VM; клиентская
  латентность включает этот участок. Поэтому клиентские числа — второй ряд,
  а не источник SLI для каталога.
- Три повтора — минимум для оценки разброса, не для статистических тестов.
