# ADR 0014. Тестовый сервис: собственный двухзвенный Go-сервис

Дата: 2026-09-13. Закрывает spec 8.8 (часть про сервис), open-questions 1.1.

## Статус

Принят.

## Контекст

Все целевые показатели считаются по «простому тестовому сервису», который не
был описан. От него зависят контракт метрик (architecture §2.3), трассировка
между звеньями (задача 3) и видимость сетевой деградации в серверных метриках
(ADR 0016). Рассматривались podinfo и собственный сервис.

## Решение

Собственный минимальный сервис на Go, модуль `test-service/`, один бинарь и
один образ, роль задаётся флагом `--role=frontend|backend`.

**Топология внутри каждого кластера федерации:** `frontend → backend`.

- `backend` — один долгоживущий Deployment на кластер, часть стенда.
  `GET /work` возвращает небольшой JSON; `GET /healthz`, `GET /metrics`.
- `frontend` — по одному Deployment на workload (ADR 0015). `GET /` вызывает
  `backend` по in-cluster Service с таймаутом (по умолчанию 1 с, флаг) и
  отдаёт результат; ошибка или таймаут backend'а — ответ `502`. `GET /healthz`
  становится готовым только после успешной пробы backend'а. `GET /metrics`.

Именно двухзвенность делает сетевую деградацию видимой в серверных метриках:
NetworkChaos на подах backend'а превращается в рост длительности и долю `502`
у frontend'а (ADR 0016).

**Метрики** (контракт architecture §2.3), клиент `prometheus/client_golang`:

| Метрика | Тип | Лейблы |
|---|---|---|
| `http_requests_total` | counter | `tier`, `route`, `method`, `status` |
| `http_request_duration_seconds` | histogram | `tier`, `route` |

Границы гистограммы включают 0.2 с (бюджет p95): `0.005, 0.01, 0.025, 0.05,
0.1, 0.15, 0.2, 0.3, 0.5, 0.75, 1, 2.5, 5`.

Лейблы `cluster` (из `external_labels` Prometheus) и `workload` (из pod-label
`federation.spbu/workload` через relabeling kube-sd) добавляет слой сбора,
а не сервис.

**Трассировка:** `otelhttp` на сервере и на клиенте frontend'а, экспорт OTLP
в in-cluster OTel Collector по `OTEL_EXPORTER_OTLP_ENDPOINT`; при пустой
переменной трассировка выключена. Подключается в задаче 3.

**Сборка:** образ собирается локально и загружается в кластеры через
`kind load docker-image`; внешний registry не нужен.

## Последствия

Плюсы:

- Полный контроль над контрактом метрик, таймаутами и поведением при ошибке
  backend'а; ничего не нужно проверять на соответствие чужому сервису.
- Один бинарь на два звена — один Dockerfile, один линт, один тест.

Минусы:

- Код и его поддержка на нас: ещё один Go-модуль в репозитории, ещё один
  `go test ./...` в `make test`.
- Сервис синтетический: без бизнес-логики, без состояния, с постоянным
  профилем ответа. Выводы о «реальном» сервисе переносятся с оговорками; это
  соответствует границам работы (vision), но фиксируется в отчёте.
- Таймаут frontend → backend (1 с) — параметр, от которого зависит, когда
  задержка 500 мс превращается в ошибку, а не только в латентность. Значение
  фиксируется в `meta.json` прогона (ADR 0008).
