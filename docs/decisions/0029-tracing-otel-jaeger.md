# ADR 0029. Трассировка: Envoy — корень трейса, OTel Collector в кластерах, Jaeger v2 в control, сэмплинг 10% на шлюзе

Дата: 2026-09-24. Реализация задачи 3 плана; уточняет spec §2.2 и §7 («OpenTelemetry +
Jaeger»), architecture §1.2 и §2.1 (OTel Collector в каждом кластере), ADR 0014
(трассировка тестового сервиса), ADR 0025 (порт 16686 под Jaeger).

## Статус

Принят.

## Контекст

spec §2.2: без сквозного трейса мультикластерная латентность не разложима на
составляющие. ADR 0014 заложил в тестовый сервис `otelhttp` и экспорт OTLP по
`OTEL_EXPORTER_OTLP_ENDPOINT`, architecture — OTel Collector в каждом кластере. Не
были решены:

- где корень трейса и что вообще «между кластерами» на стенде. Запрос клиента
  проходит шлюз в control, затем NodePort кластера федерации, frontend и backend;
  межкластерный переход ровно один — шлюз → кластер;
- кто принимает решение о сэмплинге и какой долей: трассировка меняет систему, на
  которой меряются SLO, а хранилище ограничено памятью стенда;
- как трейсы переживают стенд: Jaeger в памяти, а результат НИР — файлы прогонов;
- чем мерить сам механизм (CLAUDE.md: механизм без замера ценности не имеет).

## Решение

1. **Корень трейса — шлюз.** EnvoyProxy `telemetry.tracing`: провайдер
   OpenTelemetry, спаны в Jaeger control, `serviceName: gateway`, тег
   `federation.cluster=control`. Envoy передаёт `traceparent` (W3C) в кластер вместе
   с запросом. Один трейс покрывает control (Envoy) и кластер федерации (frontend,
   backend) — это и есть трейс «между кластерами».

2. **Сэмплинг решает только шлюз: 10%** запросов (`samplingRate: 10`). Envoy
   решает сам и внешних решений не принимает: флаг `sampled` во входящем
   `traceparent`, `x-client-trace-id` и `x-envoy-force-trace` для внешних запросов не
   учитываются (проверено на стенде). Trace id из входящего `traceparent` при этом
   сохраняется, поэтому для детерминированной проверки (дымовой тест `stand-up`)
   сэмплинг на время поднимается до 100%. Сервис использует `ParentBased(AlwaysOff)`:
   продолжает сэмплированный трейс и никогда не начинает свой. Поэтому пробы Kubernetes,
   smoke-тест и пробы DR, прямые запросы мимо шлюза не трассируются. 10% при 50 RPS —
   около 4 тыс. трейсов на 13-минутный прогон: разложение по перцентилям устойчиво, а
   память Jaeger ограничена.

3. **Тестовый сервис** (`test-service/internal/app/tracing.go`): OTel Go SDK 1.46,
   `otelhttp` v0.71 на `GET /` и `GET /work`, клиентский спан вызова backend'а,
   экспорт OTLP/HTTP батчами раз в 2 с. Без `OTEL_EXPORTER_OTLP_ENDPOINT` трассировка
   выключена (ADR 0014). Ресурс: `service.name` = роль (`frontend` | `backend`),
   `federation.tier`, `federation.workload`. Метрики — снаружи трассировки: её
   накладные расходы входят в длительность, которую видит SLI. Переменную получают
   все поды сервиса: `app` и `backend` — из манифестов стенда, workload'ы потока — от
   планировщика (`--otlp-endpoint`) и генератора в прямом режиме, одинаково для
   meta и naive.

4. **OTel Collector 0.161 (core)** в каждом кластере федерации, ns `observability`:
   OTLP/HTTP от подов → `memory_limiter` → `resource` (`federation.cluster=<id>`) →
   `batch` → OTLP gRPC в Jaeger control по IP узла и NodePort 30417 (ADR 0021, 0022).
   Метку кластера ставит слой сбора, как `external_labels` у Prometheus: сервис не
   знает, где работает. Конфиг рендерится при `stand-up`
   (`render-otel-collector.sh`), хэш конфига — в аннотации пода.

5. **Jaeger v2.21 в control** (инвариант 1: наблюдатель вне наблюдаемого), ns
   `observability`: OTLP gRPC/HTTP, хранилище в памяти, `max_traces: 20000`, UI и API
   на хост-порт 16686 (зарезервирован ADR 0025). Метрики Jaeger и коллекторов
   скрейпят Prometheus control и федерации. Датасорса в Grafana нет: он ходит в
   устаревший `/api/services`, удалённый в Jaeger 2.21; трейсы смотрятся в UI Jaeger.

6. **Трейсы прогона — файлы, как ряды (ADR 0002).** `experiments/load/export.sh`
   вызывает `experiments/traces/export.py`: трейсы окна прогона из Jaeger API v3
   (окнами по 30 с) → `traces/spans.csv.gz` (сырые спаны), `traces/decomposition.csv.gz`
   (трейс на строку, признак `in_run`) и `traces/summary.json`. Сырые спаны — за всё
   окно экспорта с запасом ±60 с, как ряды; статистика — только по трейсам, корень
   которых начался внутри прогона (`meta.json`): запас захватывает хвосты соседних
   прогонов. `export.py --offline` пересчитывает сводку из `spans.csv.gz` без Jaeger.
   Любой раннер (нагрузка, сценарии 1–3) получает трейсы автоматически. Устаревший
   `/api/traces` в Jaeger 2.21 удалён; используется только `/api/v3` (OTLP JSON).

7. **Разложение задержки** — по спанам одного трейса. У шлюза два спана:
   `ingress` (сервер, запрос целиком) и `router … egress` (клиент, вызов upstream'а;
   `spawn_upstream_span` Envoy Gateway):

   | Звено | Формула | Что внутри |
   |---|---|---|
   | `total` | `ingress` шлюза | запрос целиком, как его видит Envoy |
   | `gateway` | `ingress − egress` | собственная работа Envoy |
   | `hop` | `egress − frontend server` | сеть control → кластер, kube-proxy NodePort |
   | `frontend` | `frontend server − backend client` | работа frontend'а |
   | `backend_net` | `backend client − backend server` | сеть и kube-proxy внутри кластера |
   | `backend` | спан backend'а | работа backend'а |

   Запрос, не дошедший до кластера, даёт трейс только со спаном шлюза: он
   учитывается в `total` и ошибках, звенья пусты.

8. **Замер задачи 3** — `experiments/traces/run.sh` (`make trace-run`): 50 RPS в
   `app.fed.local` при сэмплинге шлюза 0 / 10 / 100% на одном стенде. Цена трассировки —
   разница клиентской задержки k6; польза — разложение по звеньям. Сэмплинг меняется
   на EnvoyProxy на время прогона (xDS, без перезапуска прокси) и возвращается к 10%.

## Последствия

Плюсы:

- Межкластерный переход, который метрики видят только как разницу клиентского и
  серверного рядов, измеряется напрямую, по запросу; в сценарии 2 видно, в каком
  звене растёт задержка.
- Трейсы сохраняются вместе с рядами каждого прогона и не зависят от жизни Jaeger.
- Решение о сэмплинге в одном месте; сервис не начинает трейсы сам, поэтому пробы
  и контур DR не засоряют хранилище.

Минусы:

- Трассируется только трафик через шлюз; клиентская часть (k6 → хост → docker-VM) в
  трейсе не видна: k6 не отправляет спаны.
- Клиент не может запросить трассировку конкретного запроса: Envoy не принимает
  внешнее решение о сэмплинге. Для точечной проверки сэмплинг поднимается на шлюзе
  целиком, то есть на весь трафик стенда.
- В Grafana трейсов нет: её датасорс Jaeger несовместим с API Jaeger 2.21. Трейсы и
  ряды смотрятся в двух разных UI; в анализе они соединяются по времени и кластеру.
- Базовая линия цены трассировки — сэмплинг 0%, а не бинарь без SDK: пропагация
  `traceparent` и несэмплированные спаны остаются. Их стоимость — микросекунды, но
  отдельно не измерялась.
- Сэмплинг 10% отбрасывает 90% ошибок из трейсов; tail-сэмплинг ошибок невозможен
  без сборки спанов одного трейса из двух кластеров в одном коллекторе.
- Jaeger хранит трейсы в памяти: рестарт или переполнение `max_traces` теряют то, что
  ещё не выгружено экспортом.
- Звенья — разности длительностей спанов, каждая измерена на своём узле, поэтому
  от расхождения часов между кластерами разложение не зависит. Но `hop` неделим:
  это путь запроса туда и ответа обратно вместе с установкой соединения; отдельно
  «туда» и «обратно» по трейсу не разделить.
- Ещё три пода на стенд (Jaeger в control, по коллектору в каждом кластере
  федерации) и переменная окружения, которую должны знать и планировщик, и
  генератор (форма workload'а описана дважды, ADR 0027).
