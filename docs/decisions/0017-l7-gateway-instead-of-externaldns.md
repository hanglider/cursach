# ADR 0017. L7-шлюз в control-кластере (Gateway API + Envoy Gateway) вместо ExternalDNS

Дата: 2026-09-13. Закрывает open-questions 1.5. Меняет стек spec §7.

## Статус

Принят.

## Контекст

spec §7 задавал «Ingress-nginx + ExternalDNS» для переключения трафика. На
kind-стенде у ExternalDNS нет провайдера DNS: пришлось бы поднимать свой
(CoreDNS + etcd или PowerDNS) и заставлять k6 резолвить через него. DNS не
умеет веса, а architecture §6.3 требует поэтапный возврат трафика
10% → 50% → 100%. Нужна host-based маршрутизация для потока workload'ов
(ADR 0015) и веса по кластерам на каждый хост.

Выбор реализации шлюза между nginx и Envoy был открыт. Ingress-nginx
отклонён: проект объявил о завершении сопровождения в 2026 году, а его
canary-аннотации дают веса только между двумя backend'ами. Статический Envoy
или nginx с конфигом в ConfigMap отклонены: изменение весов проходило бы
через kubelet-синхронизацию ConfigMap (до минуты), что размывает замер RTO.

## Решение

**Шлюз** — Gateway API (`gateway.networking.k8s.io`) с реализацией Envoy
Gateway в control-кластере.

- Один `Gateway` с HTTP-listener'ом; публикуется на хост через
  `extraPortMappings` kind, k6 ходит в него.
- На каждый хост — `HTTPRoute` с `backendRefs` по одному на кластер
  федерации и полем `weight`. Для `w-<n>.fed.local` вес 100 у выбранного
  кластера; долгоживущие маршруты с весами по нескольким кластерам — предмет
  открытого вопроса 2.3.
- Backend'ы — точки входа кластеров федерации по внутрисетевым адресам
  (ADR 0021): Service без селектора + EndpointSlice либо ресурс `Backend`
  Envoy Gateway; выбор при реализации задачи 1.
- **DR Controller меняет веса**, редактируя `HTTPRoute` через Kubernetes API
  control-кластера — обычный controller-runtime паттерн, изменение доходит до
  Envoy через xDS за секунды.
- Планировщик (или синхронизатор маршрутов, задача 6) создаёт `HTTPRoute`
  для нового workload'а и удаляет для умершего.
- DNS не нужен: k6 задаёт заголовок `Host`. Домен `.fed.local` — соглашение,
  а не запись где-либо.
- Метрики Envoy (per-upstream) скрейпит control-Prometheus как бонусный ряд;
  источником SLI для каталога они не являются (ADR 0016).

ExternalDNS из стека исключается.

## Последствия

Плюсы:

- Веса и маршруты — Kubernetes-ресурсы: DR Controller и планировщик работают
  с ними штатными средствами, изменения атомарны и быстры, конфигурация
  версионируется как манифесты.
- Не упирается в два кластера: при добавлении `cluster-c` меняется только
  число `backendRefs`.

Минусы:

- Шлюз — единая точка входа и отказа для всего трафика стенда. Отказ
  control-кластера роняет и наблюдателя, и трафик (см. ADR 0001).
- Ещё два пода (контроллер Envoy Gateway + прокси) и набор CRD Gateway API
  в control-кластере, порядка 200 МБ памяти.
- Точка входа в каждый кластер федерации (как трафик с шлюза доходит до
  Service `w-<n>`) требует своего решения в задаче 1: NodePort на workload,
  hostPort или лёгкий in-cluster ingress. Это второй прыжок и второй
  источник латентности на пути клиента.
- Стек spec §7 меняется: строка «Traffic switching» переписана; в отчёте
  обосновать отход от первоначального ExternalDNS.
