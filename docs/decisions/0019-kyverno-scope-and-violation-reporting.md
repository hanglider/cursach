# ADR 0019. Kyverno: политики региона и сертификаций; ресурсы на рубеже каталога; фиксация нарушений

Дата: 2026-09-13. Закрывает open-questions 3.7.

## Статус

Принят.

## Контекст

architecture §4.3 предлагал три политики Kyverno (регион, сертификации,
ресурсы) в режиме `Enforce` с `background: true` и watcher, транслирующий
PolicyReport в `POST /violations`. Политика `require-resources` в Kyverno
реализуема только через `apiCall` к узлам и суммирование requests всех подов,
что хрупко и медленно. Отдельно: ресурс, отклонённый в `Enforce`, не
существует и в PolicyReport не попадает; Kyverno публикует о нём Event.

## Решение

**Две ClusterPolicy** в каждом кластере федерации, обе `Enforce`,
`background: true`, контекст — ConfigMap `federation-system/cluster-identity`
(ADR 0009):

| Политика | Проверяет |
|---|---|
| `require-region-match` | `require-region` пуста или равна `region` кластера |
| `require-certification` | каждый элемент `require-certification` есть в `certifications` кластера |

Матчатся Deployment и Job; ресурсы без аннотаций `federation.spbu/require-*`
проходят.

**Ресурсы** (`require-cpu`, `require-memory-gi`) проверяются только на рубеже
каталога (`/clusters/eligible`, ADR 0018). In-cluster backstop для ресурсов
уже существует — kube-scheduler: под, которому не хватает ресурсов, остаётся
в `Pending`. Это отказ размещения, а не нарушение политики, и он проявится в
availability, а не в `policy_violations`.

**Фиксация нарушений в audit log** — два пути, оба ведут в
`policy_violations` с `detected_by = kyverno`:

1. Планировщик, получив отказ admission при создании ресурса, сам вызывает
   `POST /violations` (в `details.reported_via = scheduler`) и пишет решение
   с `outcome = rejected`.
2. Для размещений в обход планировщика (сценарий 3, ручной `kubectl apply`)
   — **watcher как фоновая задача каталога**: следит за Event'ами Kyverno
   с reason `PolicyViolation` и за PolicyReport'ами во всех кластерах
   федерации через те же kubeconfig'и, что нужны для проверки регистрации
   (ADR 0018). Дедупликация по кластеру, объекту и политике. Отдельный
   сервис не заводится: каталог уже владелец audit log и уже имеет доступ к
   кластерам.

При записи нарушения каталог вычисляет для требований отклонённого
workload'а список допустимых кластеров и кладёт его в
`details.eligible_clusters` — это ответ на «предлагает ли система корректный
кластер» из сценария 3.

## Последствия

Плюсы:

- Политики простые и быстрые: сравнение аннотации с полем ConfigMap, без
  `apiCall`.
- Нарушение фиксируется независимо от того, кто создавал ресурс; сценарий 3
  проверяет именно путь в обход планировщика.

Минусы:

- Kyverno не является backstop'ом для ресурсных ограничений; если каталог
  ошибётся в `cpu_available`, workload зависнет в `Pending`, и это будет
  видно только по availability. Целевой показатель «0 нарушений политик»
  относится к региону и сертификациям; в отчёте это оговаривается.
- Каталог получает watch-соединения с каждым кластером федерации; при отказе
  кластера watcher должен переподключаться, а не падать, и не должен
  влиять на остальные фоновые задачи каталога.
- `background: true` даёт PolicyReport для уже существующих нарушителей при
  каждом скане; без дедупликации watcher записал бы одно нарушение
  многократно.
