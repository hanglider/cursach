# ADR 0010. Показатель RPO снят; вместо него число потерянных запросов за инцидент

Дата: 2026-09-13. Закрывает spec 8.1, open-questions 1.7.

## Статус

Принят.

## Контекст

spec §1.3 задавал «RPO < 30 с при stateless-нагрузке». RPO — возраст
потерянных данных на момент восстановления. У stateless-сервиса нет
персистентного состояния, RPO не определён. Варианты: снять показатель,
переопределить его как окно потери запросов (дублирует RTO с более жёстким
порогом), либо добавить состояние в тестовый сервис и Velero в DR-цикл.

## Решение

Показатель RPO снимается. Вместо него в область DR вводится **число
потерянных запросов за инцидент**: запросы, завершившиеся ошибкой или
таймаутом с момента внесения отказа (время из Chaos Mesh, инвариант 7) до
завершения failover. Считает k6 напрямую; серверный ряд из Thanos — для
сверки.

Отдельный целевой порог не задаётся: при постоянных 50 RPS величина
производна от TTD и времени failover, у которых пороги есть. Показатель
фиксируется в результатах каждого прогона сценария 1 и в отчёте.

В отчёте — абзац с обоснованием: для stateless-нагрузки RPO равен нулю по
определению, и его замер не несёт информации.

## Последствия

Плюсы:

- Из тестового сервиса и DR-цикла уходят Redis, Velero и снапшоты; MinIO не
  нужен и по этой линии (ADR 0002).
- Показатель измеряется тем же инструментом, что и остальные, без
  дополнительной инфраструктуры.

Минусы:

- Область DR теряет один числовой критерий приёмки; остаются TTD и RTO.
  Меняется таблица целевых показателей spec §1.3 — это сделано с явного
  согласования.
- Формулировка RQ3 («с фиксируемыми RTO и RPO») в отчёте потребует
  уточнения; в spec RQ3 оставлен как есть с пометкой.
- Если научный руководитель будет настаивать на RPO как числе, вернуться к
  варианту с состоянием в сервисе (Redis + снапшоты в MinIO); тогда
  пересматривается и ADR 0002.
