# ADR 0030. Сценарий 2: фоновый трафик в `app`, чтобы у каждого кластера был SLI; ограничение правила 0.5

Дата: 2026-09-25. Закрывает spec 8.9, open-questions 4.1. Уточняет ADR 0005
(«Последствия»), ADR 0008 (профиль нагрузки сценария 2), ADR 0015.

## Статус

Принят.

## Контекст

Каталог считает error rate и p95 кластера по серверным метрикам всех
frontend'ов кластера за 5 мин (architecture §2.4). В сценарии 2 k6 по
ADR 0015 нагружает только поток workload'ов `w-<n>`. Долгоживущий `app`
получает лишь пробы DR на `/healthz`, а пробы не инструментируются. Если в
кластере нет живых workload'ов потока, у него нет ни error rate, ни p95. По
ADR 0005 оба слагаемых тогда нейтральные 0.5:
`score = 0.4 + 0.2·(1 − saturation) ≈ 0.55`. У кластера с трафиком при
p95 ≈ 5 мс score ≈ 0.95. Оба значения видны в каталоге: решения 10–15 и
решение 18.

Отсюда два эффекта, найденные при планировании задачи 8:

1. **Захват с холодного старта.** Первое размещение прогона — ничья и
   round-robin. Через 30 с у выбранного кластера появляются метрики, и
   умный планировщик отправляет туда весь поток.
2. **Деградировавший кластер выигрывает у пустого.** При p95 > 200 мс
   слагаемое латентности равно 0, и `score ≈ 0.5·(1 − e) + 0.15`, что
   больше 0.55 при `e < 0.2`. Утверждение из «Последствий» ADR 0005
   («кластер без метрик ... выиграет у деградировавшего») для деградации
   по латентности неверно.

В результате разница `meta` и `naive` в сценарии 2 определялась бы тем, в
какой кластер `meta` случайно собрал поток, а не реакцией на метрики.

Рассмотрены варианты:

- **правило «нет трафика — нет нарушений»**: кластер `healthy` без трафика
  получает идеальные 1 вместо нейтральных 0.5, как каталог уже трактует
  статус (ADR 0025 п. 2). Отклонено: это правка умного планировщика после
  предрегистрации ADR 0005 и 0006. Правило оптимистично: опустевший после
  деградации кластер через 5 мин выглядит идеальным, и `meta` периодически
  возвращается туда «на пробу»;
- **оба изменения вместе** — отклонено по той же причине;
- **ничего не менять, чередовать кластер отказа** — отклонено: результат
  остаётся артефактом концентрации, только с большим разбросом.

## Решение

1. **Фоновый трафик.** В сценарии 2 k6, кроме потока workload'ов (50 RPS,
   ADR 0008, 0015), шлёт постоянные **5 RPS в `app.fed.local`**. Веса шлюза
   номинальные 50/50: DR в сценарии 2 работает в режиме `observe` и маршрут
   не трогает (ADR 0031). Это отдельный сценарий k6 с тегом
   `kind=background`: в пороги k6 и в error rate сценария 2 он не входит
   (ADR 0031).
2. **SLI кластера по-прежнему по всем frontend'ам** (architecture §2.4):
   `app` деградировавшего кластера ходит в тот же backend и деградирует
   вместе с ним. Ни каталог, ни планировщик, ни формула не меняются.
   Параметры scoring остаются предрегистрированными (ADR 0006).
3. **Фоновый трафик стартует вместе с k6.** k6 стартует, когда у генератора
   есть три живых workload'а (`experiments/load/run.sh`). Первые решения
   прогона до старта k6 — ничьи, round-robin, как у наивного планировщика.
   Это часть разогрева до baseline, не окна отказа.
4. **Дефект правила 0.5 остаётся и фиксируется как ограничение.** В
   «Последствиях» ADR 0005 утверждение про деградировавший кластер
   исправлено ссылкой на этот ADR. В отчёте НИР — отдельной оговоркой:
   умный планировщик без фонового трафика в каждом кластере неустойчив, а
   исправление правила — возможная доработка вне приёмочных замеров.

## Последствия

Плюсы:

- Реалистичнее: в эксплуатации в кластере всегда есть трафик, кроме
  размещаемого. Сигнал о деградации есть независимо от того, куда
  планировщик положил поток.
- Код планировщика и предрегистрированные параметры не тронуты. Разница
  `meta` и `naive` — по-прежнему только функция выбора (инвариант 3).
- `app` под фоновым трафиком даёт в сценарии 2 ещё один ряд: SLO
  долгоживущего сервиса при деградации, без переключения трафика.

Минусы:

- Суммарная нагрузка сценария 2 — 55 RPS, а не 50 (ADR 0008). Поток
  workload'ов остаётся 50 RPS, так что метрика сценария сравнима с
  определением ADR 0015; фоновая доля оговаривается в отчёте.
- Дефект правила 0.5 не исправлен, а обойдён условиями стенда. Без фонового
  трафика умный планировщик собирает поток в одном кластере. Это результат
  о формуле, который надо честно показать, а не спрятать.
- Сигнал о деградации у кластера, из которого `meta` уже увёл поток,
  держится на 2.5 RPS `app`. Окна в 5 мин (≈ 750 запросов) для p95 и error
  rate достаточно, но шум выше, чем при полном потоке.
- В режиме `observe` DR видит ошибки `app` деградировавшего кластера и
  открывает инциденты DEGRADED. Трафик и каталог они не трогают, но в
  таблице `incidents` появляются записи сценария 2.
