# ADR 0018. API каталога: `/clusters/eligible` как единая точка hard constraints; bearer-токены

Дата: 2026-09-13. Закрывает open-questions 3.4 и 3.5.

## Статус

Принят.

## Контекст

Оба планировщика обязаны соблюдать hard constraints, иначе разница в error
rate станет смесью двух эффектов (инвариант 3). Логику фильтрации нужно
держать в одном месте. Планировщику также нельзя ходить в Prometheus
(инвариант 2), значит метрики для scoring он должен получать из каталога.
vision требует «базовые проверки доверия» для каталога.

## Решение

Принимается набор эндпоинтов architecture §3.3. Уточнения.

**`GET /api/v1/clusters/eligible`** принимает hard constraints из аннотаций
workload'а (`region`, `certification` — список, `min_cpu`, `min_memory_gi`)
и возвращает полную картину, достаточную для записи решения:

```json
{
  "eligible": [
    {"id": "cluster-a", "slo_status": "healthy",
     "metrics": {"error_rate": 0.01, "latency_p95_ms": 120,
                 "saturation": 0.4, "observed_at": "..."}}
  ],
  "rejected": [
    {"id": "cluster-b", "filtered_by": "certification:pci-dss"}
  ]
}
```

Правила фильтрации:

- регион и сертификации — по атрибутам `clusters`;
- ресурсы — по последней строке `cluster_metrics` (`cpu_available`,
  `memory_available_gi`);
- `slo_status = down` — отсеивается с `filtered_by: "down"`: размещение в
  мёртвый кластер невозможно физически, это не soft-предпочтение;
- `unknown` и `degraded` **остаются** в `eligible` (инвариант 6): отсутствие
  метрик — не основание для исключения. Умный планировщик учитывает
  `degraded` через scoring, наивный — никак; это и есть измеряемая разница.

Метрики в ответе — последний снимок из `cluster_metrics`; планировщику не
нужен второй запрос и не нужен Prometheus. Кэшировать ответ в планировщике
нельзя (ADR 0003).

**Аутентификация** — статические bearer-токены, по одному на компонент:

| Токен | Кому | Права |
|---|---|---|
| `scheduler` | Meta-Scheduler (оба режима) | `GET /clusters*`, `POST /decisions`, `POST /violations` |
| `dr-controller` | DR Controller | `GET /clusters*`, `PATCH /clusters/{id}/status` |
| `admin` | скрипты стенда, человек | всё |

Токены генерируются при `make stand-up`, лежат в `.env` (в git не
попадает, есть `.env.example`) и в Secret'ах control-кластера. `/healthz`
без токена. mTLS не делаем: для стенда избыточно.

**Проверка при регистрации:** каталог читает `cluster-identity` (ADR 0009)
по `api_endpoint` через kubeconfig, смонтированный в под каталога, и
отказывает при расхождении. Это и есть «базовая проверка доверия».

## Последствия

Плюсы:

- Hard constraints реализованы и тестируются один раз, в Python, с
  unit-тестами на каждое правило; оба планировщика получают их бесплатно.
- Ответ содержит всё, что нужно для строки `placement_decisions` (ADR 0004).

Минусы:

- Каталог становится обязательным для каждого размещения; его недоступность
  останавливает оба планировщика. Планировщик в этом случае пишет решение
  с `outcome = no_candidates` и причиной, а не размещает «наугад».
- Статические токены не отзываются по отдельности без перезапуска; ротации
  нет. Для стенда приемлемо.
- Каталогу нужны kubeconfig'и всех кластеров федерации (для проверки
  регистрации и для watcher'а нарушений, ADR 0019). Это ещё один Secret,
  который создаёт `stand-up` из `kind get kubeconfig --internal`.
