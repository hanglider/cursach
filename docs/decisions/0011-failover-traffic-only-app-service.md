# ADR 0011. Failover переключает только трафик; объект переключения — долгоживущий сервис `app`

Дата: 2026-09-13. Закрывает spec 8.6, open-questions 2.3.

## Статус

Принят.

## Контекст

Meta-Scheduler размещает новые workload'ы; DR переключает трафик. Что
происходит с уже размещёнными workload'ами при отказе кластера и что тогда
означает RTO — не было определено. После ADR 0015 и 0017 вопрос обострился:
у каждого workload'а потока свой хост и ровно один кластер, вес 100 на одном
`backendRef`. «Переключить трафик» для такого маршрута некуда.

## Решение

**1. Долгоживущий сервис `app`** — часть стенда, как backend:

- frontend тестового сервиса (ADR 0014) в каждом кластере федерации, две
  реплики, `WORKLOAD=app`, Service NodePort с фиксированным портом 31998;
- один маршрут `app.fed.local` на шлюзе с `backendRefs` на каждый кластер,
  номинальные веса 50/50; создаётся `make stand-up`, адреса узлов по IP
  (ADR 0022).

`app` — объект переключения трафика для DR и цель его пробы (ADR 0007).

**2. Failover — только трафик.** На DOWN DR Controller ставит вес отказавшего
кластера в 0; на RECOVERING возвращает ступенями 10% → 50% → 100% от номинала
(при двух кластерах: 5 → 25 → 50). Каталог получает `down` (ADR 0003), и
планировщик перестаёт размещать в этот кластер.

**3. Workload'ы потока** в отказавшем кластере не переносятся: они умирают
по `TTL` (ADR 0015), новые размещаются в здоровый кластер. Планировщик
остаётся без состояния.

**4. Два трафика — два сценария.**

| Сценарий | Трафик k6 | Что измеряется |
|---|---|---|
| 1, отказ кластера | `app.fed.local`, 50 RPS | TTD, RTO, SLO за инцидент, потерянные запросы; с DR vs без |
| 2, деградация сети | поток `w-<n>.fed.local`, 50 RPS (ADR 0015) | error rate и p95 при умном vs наивном |

Поток может работать во время сценария 1 для реалистичности, но измеряемый
объект там — `app`.

**5. RTO** = от внесения отказа до завершения переключения трафика
(ADR 0007). Перепланирование работающих workload'ов (вариант Б) —
расширение после задачи 8, если останется время; тогда добавляется второй
показатель `rto_workloads`.

## Последствия

Плюсы:

- Вопрос «что переключает DR» получил конкретный ответ; сценарий 1 измерим
  на одном хосте `app.fed.local`.
- Планировщик и DR остаются независимыми: ни один не хранит желаемых
  размещений.
- Сравнение «с DR vs без» наглядно: без DR веса остаются 50/50 и половина
  запросов к `app` падает весь инцидент.

Минусы:

- На стенде два объекта трафика и два k6-профиля; в отчёте их нельзя
  смешивать.
- RTO ничего не говорит о времени подъёма подов в другом кластере: это RTO
  трафика, не RTO нагрузки. Формулировка в отчёте обязательна.
- `app` совмещает роль SLO-носителя и цели пробы; его отказ при здоровом
  кластере — ложный DOWN (см. ADR 0007).
- Ещё два пода на кластер федерации и один маршрут с весами, который должен
  создаваться при `stand-up` и переживать пересоздание кластеров.
