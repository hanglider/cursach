# ADR 0004. Схема данных каталога; `placement_decisions` хранит всех кандидатов

Дата: 2026-09-13. Закрывает open-questions 3.3.

## Статус

Принят.

## Контекст

spec §4.3 перечисляет атрибуты кластера и требует audit log решений и
нарушений, но схему не задаёт. Сравнительный анализ (задача 9) и
sensitivity-анализ весов scoring (open-questions 2.1) требуют знать не только
выбранный кластер, но и всех кандидатов с их метриками на момент решения.

## Решение

Принимается схема architecture §3.2: таблицы `clusters`, `cluster_metrics`,
`placement_decisions`, `policy_violations`. Уточнения:

1. `placement_decisions.candidates` хранит **всех** кандидатов, включая
   отсеянных, в виде:

   ```json
   [
     {"cluster": "cluster-a", "score": 0.83,
      "metrics": {"error_rate": 0.01, "latency_p95_ms": 120,
                  "saturation": 0.4, "observed_at": "..."},
      "filtered_by": null},
     {"cluster": "cluster-b", "score": null,
      "metrics": null, "filtered_by": "certification:pci-dss"}
   ]
   ```

   Снимок метрик кладётся прямо в запись решения, а не восстанавливается
   join'ом с `cluster_metrics` по времени: так решение можно пересчитать с
   другими весами офлайн без неоднозначности «какие метрики видел
   планировщик».

2. `scheduler_kind` ∈ {`meta`, `naive`} — оба планировщика пишут в одну
   таблицу, один каталог на все эксперименты.

3. `clusters.slo_status` ∈ {`healthy`, `degraded`, `down`, `unknown`},
   правила записи — ADR 0003.

4. `cluster_metrics` отделена от `clusters`: пишется каждые 30 с, растёт
   на ~6 тыс. строк в сутки при двух кластерах; ротация не нужна на горизонте
   работы.

5. Миграции — SQL-файлы в `registry/migrations/`, применяются при старте
   сервиса. Инструмент применения выбирается в задаче 4.

Инвариант 5 architecture §9: размещение без записи в `placement_decisions` —
дефект.

## Последствия

Плюсы:

- Задача 9 и sensitivity-анализ делаются из одной таблицы без повторных
  прогонов chaos.
- Наивный и умный планировщик разделяются одним полем.

Минусы:

- JSONB-поле `candidates` не нормализовано: запросы вида «сколько раз
  cluster-b отсеивался по сертификации» требуют JSONB-операторов или
  разворачивания в `analysis/`. Для объёмов стенда приемлемо.
- Снимок метрик дублирует `cluster_metrics`; при изменении набора метрик
  придётся менять обе точки записи.
