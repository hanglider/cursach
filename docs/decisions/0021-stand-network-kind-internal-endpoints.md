# ADR 0021. Сеть стенда: одна docker-сеть kind, внутрисетевые адреса в каталоге

Дата: 2026-09-13. Закрывает open-questions 3.9.

## Статус

Принят.

## Контекст

Компоненты control-кластера должны достигать API-серверов и сервисов
кластеров федерации: Thanos Querier — sidecar'ов, планировщик и каталог —
API-серверов, шлюз — точек входа сервиса. kind по умолчанию публикует API
на `localhost:<порт>` хоста, что изнутри другого kind-кластера недоступно.

## Решение

- Все три кластера создаются в docker-сети `kind`, которую kind заводит сам;
  отдельная сеть не нужна.
- `api_endpoint` в каталоге и kubeconfig'и для компонентов контура берутся
  из `kind get kubeconfig --internal`: адрес вида
  `https://cluster-a-control-plane:6443`, имя контейнера резолвится
  docker-DNS внутри сети.
- Сервисы федерации, к которым обращается control-кластер (Thanos sidecar,
  точки входа тестового сервиса), публикуются на узлах кластера через
  NodePort или hostPort и адресуются как `<контейнер узла>:<порт>`.
- На хост наружу выходят только шлюз (для k6) и Grafana, через
  `extraPortMappings` control-кластера. Разрешение имён контейнеров из подов
  control-кластера проверяется в задаче 1; если docker-DNS из подов
  недоступен, используются IP контейнеров с фиксацией в `stand/`.

## Последствия

Плюсы:

- Почти нулевая работа: kind уже делает нужное.
- kubeconfig'и с внутренними адресами одинаково работают для каталога,
  планировщика и DR-контроллера.

Минусы:

- IP контейнеров docker может выдавать заново после перезапуска; поэтому
  адреса — DNS-имена, а не IP, и `stand-up` перерегистрирует кластеры в
  каталоге при каждом подъёме.
- Kubeconfig'и с внутренними адресами не работают с хоста; для ручной
  отладки нужен второй набор (`kind get kubeconfig` без `--internal`).
  Оба набора — в `.gitignore`.
- NodePort/hostPort на узлах kind — второй прыжок на пути трафика
  (ADR 0017), плюс необходимость следить за коллизиями портов между
  кластерами на одном хосте.
