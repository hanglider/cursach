# ADR 0035. Задача 9: гипотезы, правило решения, вторичный ряд сценария 2, анализ чувствительности

Дата: 2026-09-27. Закрывает spec 8.14, 8.15, open-questions 6.1, 6.2 (оба
пункта делегированы, приняты рекомендованные варианты). Уточняет ADR 0006
(sensitivity) и ADR 0031 (ряды сценария 2), дополняет ADR 0025, п. 10.

## Статус

Принят.

## Контекст

Ожидаемый результат задачи 9 — «количественные результаты по гипотезам»
(spec §5), но гипотезы нигде не сформулированы. Есть исследовательские
вопросы RQ1–RQ5 (spec §1.2) и критерии приёмки (spec §1.3). На каждую
конфигурацию снято по три повтора (ADR 0008) — этого хватает для оценки
разброса, но не для статистических тестов.

График серии `task8-s2` показал, что примерно со 150–180 с отказа в
деградировавший кластер не идёт трафик потока ни в одном режиме. Workload'ы,
размещённые туда до отказа, истекают по TTL, а размещённые во время отказа не
проходят готовность. Приёмочное окно ADR 0031 (весь отказ, 300 с) разбавлено
нулями обоих режимов.

ADR 0006 требует офлайн-анализа чувствительности к весам, но не задаёт, какие
решения пересчитывать, как проверять сам пересчёт и как разрешать ничьи.
ADR 0025, п. 10 обещает сверку того, что видел каталог, с рядами Thanos.

Отклонённые варианты по гипотезам — bootstrap-интервалы по запросам k6
(запросы внутри прогона коррелируют через состояние стенда, интервал обманчиво
узок; единица наблюдения — прогон) и гипотезы шире §1.3 (расширение области).
По сценарию 2 отклонены перенос приёмки на окно 180 с (смена критерия после
прогонов) и оговорка без числа.

## Решение

1. **Гипотезы — критерии приёмки §1.3, привязанные к RQ:**
   - **H1 (RQ1).** В штатном режиме availability ≥ 99.0% и p95 < 200 мс при
     50 RPS; burn-rate алерт срабатывает при отказе.
   - **H2 (RQ2, RQ3).** DR даёт TTD < 60 с, RTO < 5 мин и меньше потерянных
     запросов, чем `observe`.
   - **H3 (RQ4).** В `enforce` 0 размещённых нарушителей; в `audit` нарушители
     размещаются и фиксируются в каталоге.
   - **H4 (RQ5).** Error rate потока у meta ниже, чем у naive, на ≥ 20%
     (ADR 0031).
   - **H5 (RQ5, ADR 0006).** Вывод H4 устойчив к весам: в каждой точке сетки
     весов с `w1 + w2 > 0` расчётная доля размещений в деградировавший кластер
     в окне отказа ниже, чем у naive в тех же прогонах. При `w1 = w2 = 0` score
     не видит ни ошибок, ни латентности, и эта точка из условия исключена.
2. **Правило решения.** Гипотеза подтверждена, если показатель достигнут на
   среднем трёх повторов **и** эффект того же знака в каждом повторе, а для
   парных сравнений — в каждой паре. Для счётных целей (0 нарушителей,
   TTD < 60 с) условие проверяется в каждом прогоне. p-значений нет (ADR 0008).
   Составная гипотеза подтверждена, только если подтверждены все её части;
   иначе — «частично», с перечнем неподтверждённых частей.
3. **Штатный режим для H1** — окна baseline (3 мин до внесения отказа) всех
   прогонов сценариев 1 и 2 задачи 8, клиентский ряд k6: `app.fed.local` в
   сценарии 1, поток в сценарии 2. Burn-rate алерт — ряд `ALERTS` из экспорта
   прогона. Приёмочная часть H1 — по окнам прогонов, в которых он мог
   сработать.
4. **Сценарий 2: вторичный ряд.** Приёмка H4 — как в ADR 0031, на окне
   [Apply, Recover]. Рядом, не для приёмки, — error rate на окне
   [Apply, Apply + 180 с] и доля размещений, не ставших готовыми, по режимам:
   вред, который error rate не видит (на неготовый workload трафика нет).
5. **Анализ чувствительности** (уточняет ADR 0006, п. 4):
   - пересчитываются все решения `placed` серии `task8-s2`, обоих режимов: у
     naive снимок метрик кандидатов тоже есть (ADR 0020);
   - слагаемые score пересчитываются по снимку метрик формулой ADR 0005
     (нейтральные 0.5 — для отсутствующей метрики, метрики старше 60 с
     относительно `decided_at` и кластера без снимка). Реализация на Python
     проверяется тестом: на решениях meta пересчёт совпадает с записанными
     Go-планировщиком `terms` и `score` (допуск 1e-9);
   - сетка — симплекс весов с шагом 0.1, 66 точек;
   - ничья (разница меньше 1e-6) делит решение поровну между равными, а не
     разрешается round-robin: офлайн очерёдности нет;
   - результат — доля решений, где выбор отличается от выбора при базовых
     весах, и расчётная доля размещений в деградировавший кластер в окне
     отказа по точкам сетки, с тепловой картой на симплексе.
6. **Сверка каталога с Thanos** (ADR 0025, п. 10): снимки `cluster_metrics`
   (error rate, p95) сравниваются с рядами `cluster:*:ratio5m` и `p95_5m` из
   экспорта в ближайшей точке не дальше шага выгрузки (5 с). Результат —
   медиана и максимум расхождения по метрике: проверка, что планировщик видел
   то же, что Prometheus.
7. **Артефакт** — `analysis/task9.py` (`make analysis`) пишет
   `analysis/task9/results.{md,json}` и графики. Всё — из данных
   `experiments/results/`, стенд не нужен. Интерпретация текстом — в отчёте
   (задача 10), не в генерируемом файле.

## Последствия

Плюсы:

- Гипотезы не выходят за критерии приёмки; правило решения честное при трёх
  повторах и не прячет разброс за средним.
- H5 превращает обязательный по ADR 0006 анализ чувствительности в проверяемое
  утверждение с заранее объявленным условием.
- Вторичный ряд объясняет абсолютные числа сценария 2, не трогая
  предрегистрированную приёмку.

Минусы:

- Правило «тот же знак в каждом повторе» при трёх повторах слабое: оно
  отсекает противоречивые результаты, но не доказывает эффект. В отчёте это
  прямо так и называется.
- H5 опирается на долю размещений, а не на error rate: пересчитать error rate
  для других весов без прогонов нельзя. Доля размещений — посредник, её связь
  с error rate видна по сериям, но не доказана для каждой точки сетки.
  Офлайн-пересчёт к тому же не учитывает, что иное решение изменило бы метрики
  кластеров (минус ADR 0006).
- H1 сформулирована до того, как были посмотрены ряды `ALERTS`. Сразу после
  стало видно, что в сценарии 1 алерт не срабатывает ни в одном прогоне:
  серверный SLO федерации не видит отказа кластера (open-questions 6.3).
  Гипотеза не переформулируется задним числом: её часть про алерт получает
  результат по данным.
