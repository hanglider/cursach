# ADR 0025. Реализация каталога: стек и миграции, пороги статуса, `PATCH` решения, размещение в control

Дата: 2026-09-14. Реализация задачи 4 плана; уточняет architecture §3 и §7.

## Статус

Принят.

## Контекст

ADR 0004 и 0018 задают схему и API каталога, но оставляют на задачу 4:
инструмент миграций; пороги `slo_status` (spec §4.3 говорит «по порогам»,
ADR 0007 даёт только error rate 0.05); откуда планировщик берёт id решения
для метки `federation.spbu/decision-id` (ADR 0009), если исход admission
известен только после создания ресурса; доступ к API с хоста; когда делать
watcher нарушений (ADR 0019); где в control живёт контур. Отдельно: что
считать `unknown`, если у кластера нет трафика и часть recording rules
даёт NaN.

## Решение

1. **Стек.** FastAPI + asyncpg, чистый SQL без ORM. Миграции — SQL-файлы
   `registry/migrations/NNNN_*.sql`; сервис применяет их сам при старте
   (таблица `schema_migrations`, advisory lock). Alembic и yoyo отклонены:
   четыре таблицы и один экземпляр не оправдывают ещё один инструмент.
   Схема ADR 0004 дополнена колонкой `placement_decisions.scoring JSONB`,
   которую требует architecture §5.2.
2. **Пороги статуса.** `degraded` — error rate за 5 мин > 0.05 (порог
   ADR 0007) **или** p95 за 5 мин > 200 мс (latency budget spec §1.3);
   `healthy` — иначе; `unknown` — у кластера нет ни одного ряда в ответе
   Thanos (недоступен Querier или store этого кластера). Частичный снимок
   без трафика (error rate и p95 отсутствуют, saturation есть) — `healthy`:
   кластер жив, нарушений SLO нет. Снимок пишется в `cluster_metrics` каждый
   цикл, в том числе пустой (все NULL): отсутствие данных видно в истории.
3. **Опрос.** Один instant-запрос `{__name__=~"cluster:…|node:…"}` с
   `partial_response=true` по recording rules ADR 0024;
   `cpu_available = allocatable × (1 − cpu_saturation)`,
   `memory_available_gi` аналогично. Запись статуса — compare-and-set: если
   между чтением и записью DR Controller поставил `down`, запись опроса не
   применяется (ADR 0003).
4. **Ресурсные hard constraints fail-closed.** `min_cpu` и `min_memory_gi`
   без снимка ёмкости отсеивают кандидата (`cpu:<n>`): непроверенное
   ограничение не считается выполненным. Несколько причин отсева
   перечисляются в `filtered_by` через запятую в фиксированном порядке:
   `down`, регион, сертификации, CPU, память.
5. **`PATCH /api/v1/decisions/{id}`** (тело `{outcome}`, токен `scheduler`).
   Планировщик записывает решение с `outcome = placed` до создания ресурса,
   получает id для метки `decision-id`, а при отказе admission меняет
   исход на `rejected` и пишет `POST /violations`.
6. **`POST /api/v1/violations`** принимает необязательные `requirements`
   (hard constraints отклонённого workload'а); каталог дописывает
   `details.requirements` и `details.eligible_clusters` (ADR 0019).
7. **`POST /api/v1/clusters` — upsert.** Повторная регистрация обновляет
   атрибуты, `slo_status` и историю метрик не трогает (ADR 0021:
   перерегистрация при каждом `stand-up`). Ответ 201 при создании, 200 при
   обновлении.
8. **Размещение.** Namespace `federation` в control для всех компонентов
   контура (каталог, планировщик, DR-контроллер). PostgreSQL 17 с PVC 1 Gi.
   Service NodePort 30800 → хост 8000 через `extraPortMapping` control;
   заодно зарезервирован 30686 → 16686 под Jaeger (задача 3), чтобы не
   пересоздавать кластер второй раз. Токены и пароль БД генерирует
   `stand-up` в `.env` (`.env.example` в репозитории) и кладёт в Secret'ы
   `registry-tokens`, `registry-db`; внутрисетевые kubeconfig'и федерации —
   Secret `federation-kubeconfigs`.
9. **Watcher нарушений Kyverno** (ADR 0019) реализуется в задаче 5 вместе
   с политиками: без Kyverno его нечем проверить. В задаче 4 — таблица
   и `POST /violations`.
10. **Замер.** `experiments/load/export.sh` выгружает `clusters`,
    `cluster_metrics`, `placement_decisions`, `policy_violations` за окно
    прогона в `experiments/results/<run-id>/registry/*.csv`: сверка того,
    что видели планировщик и DR, с рядами Thanos — задача 9.
11. **Тесты.** Правила (`app/rules.py`) — чистые функции с unit-тестом на
    каждое правило; API и опрос — на PostgreSQL в docker (testcontainers).
12. **Дефекты задачи 2, найденные первым потребителем метрик.** Правило
    `cluster:http_errors:rate*` без единого 5xx давало пустоту вместо нуля,
    и error rate отсутствовал при идеальном трафике (для scoring это
    нейтральные 0.5 вместо заслуженной единицы); исправлено через
    `or vector(0)`. Prometheus control был без
    `--web.enable-remote-write-receiver`, k6 получал 404 и клиентские ряды
    не писались; флаг добавлен в общий манифест. Прогон `stand-baseline`
    снят до этих исправлений и клиентских рядов не содержит.

## Последствия

Плюсы:

- Hard constraints и правило приоритета статуса покрыты тестами в одном
  месте; оба планировщика и DR получают их через API.
- Каталог поднимается из репозитория одной командой вместе со стендом,
  регистрация кластеров — часть `stand-up`.
- История снимков и решений выгружается вместе с рядами Thanos, у задачи 9
  один источник данных.

Минусы:

- Самописный применятель миграций не умеет откат; ошибка схемы
  исправляется следующей миграцией вперёд.
- `degraded` каталога (error rate 5 мин или p95) и DEGRADED DR-контроллера
  (error rate 1 мин и пробы) не совпадают по построению; ADR 0007 это уже
  оговаривает, добавляется расхождение по latency.
- Fail-closed по ресурсам: при недоступном Thanos workload'ы с
  `require-cpu` или `require-memory-gi` не размещаются нигде. Workload'ы
  сценариев 1–3 ресурсных требований не несут.
- `placed` записывается до создания ресурса: при падении планировщика между
  записью и созданием в audit log остаётся решение без ресурса. Ловится
  сверкой с меткой `decision-id` на ресурсах.
- Пустые снимки растят `cluster_metrics` и при недоступном Thanos; объём
  несущественный.
- Хост-порт потребовал пересоздания control-кластера; данные Prometheus
  control до 2026-09-14 потеряны, результаты прогонов уже были в
  `experiments/results/`.
- `make test` зависит от docker; без него тесты API каталога не идут.
- Токены в `.env` на хосте и в Secret'ах без шифрования — граница доверия
  стенда (ADR 0018).
