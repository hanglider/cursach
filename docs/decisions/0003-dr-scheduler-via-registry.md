# ADR 0003. DR Controller и Meta-Scheduler взаимодействуют только через каталог

Дата: 2026-09-13. Закрывает spec 8.5, open-questions 3.2.

## Статус

Принят.

## Контекст

spec §4.6 говорит, что DR Controller «уведомляет meta-scheduler» о failover.
Протокол не задан: прямой вызов API, Kubernetes-ресурс или обновление
каталога. Прямая связь создала бы второй источник истины о здоровье кластера
и связность двух контроллеров, которые по плану пишутся в разные недели.

## Решение

Единственный канал — каталог, поле `clusters.slo_status`.

- DR Controller выставляет `down` через `PATCH /api/v1/clusters/{id}/status`
  при переходе кластера в состояние DOWN и снимает его при восстановлении.
- Meta-Scheduler перед каждым решением вызывает `/api/v1/clusters/eligible`
  (ADR 0018); кластеры со статусом `down` в кандидаты не попадают.
- Компоненты не знают о существовании друг друга.

Правило приоритета записи в `slo_status`, чтобы фоновый опрос каталога не
затирал решение DR-контроллера:

| Кто пишет | Какие значения | Условие |
|---|---|---|
| Фоновый опрос каталога (30 с) | `healthy`, `degraded`, `unknown` | только если текущий статус не `down` |
| DR Controller | `down`, и снятие `down` | всегда |

`unknown` выставляет только каталог (метрики не получены), `down` — только
DR Controller (инвариант 6: `unknown` ≠ `down`).

## Последствия

Плюсы:

- Один источник истины о состоянии кластера; audit log решений планировщика
  ссылается на тот же статус, что видел DR.
- Контроллеры разрабатываются и тестируются независимо, с каталогом в роли
  единственного контракта.

Минусы:

- Задержка реакции планировщика на failover — до одного цикла его обращения
  к каталогу; при решении на каждое размещение это доли секунды, но при
  кэшировании ответов каталога задержка вырастет. Кэшировать `eligible` в
  планировщике нельзя.
- Каталог становится критическим для DR-цикла: недоступен каталог — DR не
  может «сообщить» о failover, и новые размещения продолжают идти в мёртвый
  кластер. Для стенда приемлемо; фиксируется как ограничение.
- Поле `slo_status` совмещает два источника (метрики и DR) и требует правила
  приоритета выше; правило должно быть покрыто тестом каталога.
