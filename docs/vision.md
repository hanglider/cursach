# Vision: надёжность и управление размещением в федерации Kubernetes-кластеров

> Документ верхнего уровня: зачем эта работа и что считается успехом.
> Не содержит деталей реализации — они в `docs/spec.md` и `docs/architecture.md`.
> При конфликте с ними приоритет у этого документа: он описывает намерение.

## Контекст

Федерация Kubernetes — несколько независимых кластеров, объединённых общей
плоскостью управления. Кластеры живут в разных регионах, у разных провайдеров,
и продолжают работать автономно при недоступности управляющей плоскости.

Два свойства такой архитектуры задают всю задачу:

1. **Кластеров несколько → отказы неизбежны и нормальны.** Вопрос не в том,
   упадёт ли площадка, а в том, что происходит с сервисом, когда она падает.
2. **Нельзя «запускать где угодно».** Регион, требования к данным, метки
   безопасности, регуляторные ограничения — всё это сужает множество
   допустимых кластеров для каждой конкретной нагрузки.

Инструменты для отдельных подзадач существуют и зрелые. Разрозненность этих
инструментов и есть предмет работы: решение о размещении нагрузки принимается
без учёта того, что происходит с кластерами прямо сейчас.

## Проблема

Оператор федерации сегодня вынужден вручную координировать несколько
несвязанных систем. Наблюдаемость знает, что кластер деградирует. Планировщик
об этом не знает и продолжает направлять туда нагрузку. Политики размещения
проверяются внутри одного кластера и ничего не знают о соседних.
Восстановление после аварии описано текстом в runbook, а не выполняется кодом.

Следствие: время реакции на инцидент определяется квалификацией и доступностью
дежурного инженера, а не свойствами системы.

## Цель

Сделать надёжность федерации **измеримой** и улучшать её **практическими
механизмами**, проверяя каждое улучшение экспериментом.

Обе половины формулировки одинаково важны. «Измеримая» означает, что до и
после внедрения любого механизма есть числа, которые можно сравнить.
«Практические» означает работающий код на стенде, а не описание архитектуры.

## Ключевая идея: сквозной контур управления

```
Наблюдаемость → SLO → Политики → Выбор кластера → DR-готовность
```

Каждое звено питает следующее данными:

- **Наблюдаемость** показывает фактическое качество работы каждого кластера
- **SLO** превращает это качество в цель и в критерий успеха
- **Политики** отсекают недопустимые площадки для конкретной нагрузки
- **Meta-scheduler** выбирает лучшее из того, что осталось допустимым
- **DR-процедуры** возвращают систему в рабочее состояние воспроизводимо

Замкнутость контура — главное отличие от набора отдельных инструментов.
Решение о размещении принимается с учётом текущего состояния, а не только
статических атрибутов кластера.

## Исследовательские вопросы

1. Как измерять надёжность мультикластера через SLO, агрегируя метрики из
   нескольких независимых кластеров?
2. Какие механизмы реально улучшают SLO при типовых сбоях, а какие только
   выглядят полезными?
3. Как обеспечить воспроизводимый DR-цикл: обнаружение → failover →
   управляемый подъём?
4. Как убрать ручные ошибки размещения через исполняемые (machine-readable)
   политики?
5. Как выбирать кластер осмысленно — по latency, ошибкам и риску — и лучше ли
   это наивного выбора?

Пятый вопрос — центральный. Остальные четыре создают данные и условия, при
которых на него можно ответить количественно.

## Что делаем

- **Стенд:** 2–3 Kubernetes-кластера с простым тестовым сервисом и нагрузкой
- **Наблюдаемость:** Prometheus + Grafana для метрик, OpenTelemetry для
  сквозной трассировки запросов между кластерами
- **Контролируемые эксперименты со сбоями:** падение части кластера,
  деградация сети, отключение узлов
- **Механизмы улучшения:** переключение трафика, корректное размещение,
  автоматизация восстановления

Формат работы во всех случаях один: замер до → внедрение механизма → замер
после → сравнение на одинаковых сценариях.

## Компоненты решения

**Policy-based placement.** Правила «куда можно размещать workload»:
labels, affinity, taints на уровне Kubernetes плюс движок политик
(Kyverno или OPA Gatekeeper) для enforcement.

**Федеративный каталог.** Реестр кластеров: регистрация ресурсов, метаданные,
базовые проверки доверия. REST-сервис на FastAPI + PostgreSQL с
аутентификацией. Отвечает на вопрос «какие кластеры вообще существуют и в
каком они состоянии».

**Meta-scheduler.** Применяет политики к списку кластеров из каталога,
учитывает метрики качества, выбирает площадку. Обязательно реализуется в двух
вариантах — «умном» и наивном — иначе сравнивать не с чем.

## Критерии успеха

| Область | Что измеряем |
|---|---|
| SLO | Доля успешных запросов, latency-порог, поведение при сбоях |
| DR | Время обнаружения, время восстановления, потенциальная потеря данных |
| Размещение | Число нарушений политик и предотвращённых ошибок |
| Планировщик | Изменение error rate и задержек относительно наивного выбора |

Конкретные пороговые значения задаются в `docs/spec.md`. Здесь важен принцип:
каждая область имеет число, а не качественную оценку.

## Артефакты на выходе

- Стенд со сценариями отказов и дашбордами
- Воспроизводимый DR-план — исполняемый, не текстовый
- Набор политик размещения
- Прототип meta-scheduler'а

Требование к каждому: воспроизводимость на чистой машине из репозитория.
Артефакт, который запускается только у автора, работой не считается.

## Границы работы

Явно **не** входит в задачу:

- Production-ready решение. Цель — прототип и методика измерения.
- Работа с реальными облачными провайдерами. Стенд локальный.
- Оптимизация стоимости размещения. Только надёжность и соответствие политикам.
- Stateful-нагрузки со сложной репликацией данных. Базовый сценарий —
  stateless-сервис.
- Замена существующих federation-решений. Работа исследует недостающее звено,
  а не переписывает экосистему.

## Принципы

1. **Измеримость важнее полноты.** Один механизм с честными числами до/после
   ценнее трёх реализованных без замеров.
2. **Сравнение с базовым вариантом обязательно.** Любое «умное» решение
   существует в паре с наивным, на одних и тех же сценариях.
3. **Воспроизводимость.** Эксперимент, который нельзя повторить, — не
   результат.
4. **Отказ — штатное состояние.** Система проектируется от сценария отказа,
   а не от happy path.

## Открытые вопросы

Требуют решения до начала реализации:

- Как агрегировать метрики нескольких независимых Prometheus в единую картину
- Какие именно сбои считать «типовыми» и как их воспроизводить контролируемо
- Где проходит граница между hard- и soft-ограничениями размещения
- Что именно считать «инцидентом» с точки зрения автоматики: какой сигнал
  запускает failover
- Как избежать флаппинга при переключении трафика туда-обратно

## Глоссарий

| Термин | Значение в этой работе |
|---|---|
| Федерация | 2+ Kubernetes-кластера под общим управлением |
| Workload | Единица нагрузки для размещения (Deployment, Job) |
| SLI / SLO | Индикатор качества / целевое значение по нему |
| Meta-scheduler | Планировщик уровня федерации, выбирающий кластер |
| Hard constraint | Ограничение, нарушение которого недопустимо |
| Soft constraint | Предпочтение, влияющее на ранжирование |
| DR-цикл | Обнаружение → failover → восстановление → возврат трафика |
| Стенд | Локальное окружение для экспериментов |
