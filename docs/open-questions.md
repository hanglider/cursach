## 8. Масштабирование федерации: серия по числу кластеров N

Поводом стала облачная VM на 32 GB (обсуждение 2026-10-17): с ней перестаёт
действовать ограничение памяти ADR 0013 и architecture §7.1. Цель — не просто
прогнать стенд крупнее, а ответить на новый вопрос: **как эффект контура и его
собственная цена зависят от N**. Сейчас у результата одна точка, N = 2, и после
деградации у `meta` остаётся единственный кандидат. Требования к хосту описаны
в `stand/README.md`, раздел «Хост на Linux и в облаке».

### 8.1. Входит ли серия по N в работу и как её оформить (spec 8.18)

**Контекст.** vision («2–3 Kubernetes-кластера») и spec §1.1 («стенд из
2–3 кластеров») фиксируют размер стенда, а CLAUDE.md запрещает расширять
область без явного согласования. Задачи 1–9 закрыты, впереди задача 10.
Целевые показатели spec §1.3 сняты на N = 2 (`task8-s2c`, снижение 45.6%).
Руководитель видел план этапа 2, и в `docs/nir/supervisor-meeting.md` есть
блок вопросов к нему.

**Варианты.**

- **А. Новый пункт плана после задачи 9, сверх целевых показателей.** Приёмка
  остаётся на `task8-s2c`, серия по N идёт отдельным результатом. Правки
  vision (граница «2–3» → «2–5 для серии масштабирования»), spec §1.1 и §5,
  architecture §7.1, ADR. Минус: время до отчёта и новая разработка на стенде.
- **Б. Не делать.** Масштабирование упоминается в отчёте как направление
  дальнейшей работы вместе с ограничением architecture §7.1. Минус: RQ5
  остаётся с одной точкой.
- **В. Перенести приёмку на серию по N.** Не рекомендую: это изменение
  критериев приёмки задним числом.

**Рекомендация:** А, после разговора с руководителем.

### 8.2. Какие значения N (spec 8.19)

**Контекст.** Серия сценария 2 (3 повтора × meta/naive) идёт ~1.5–2 ч на одно
значение N. Стенд ни разу не поднимался с N > 2.

**Варианты.**

- **А. N = 2, 3, 4, 5:** ~7 ч машинного времени, кривая по четырём точкам.
- **Б. N = 2, 3, 5:** ~5 ч, три точки.
- **В. N = 2 и 5:** ~3.5 ч, только концы, форму зависимости не видно.

**Рекомендация:** А. По деньгам разница между вариантами мала, а время уходит
в основном на подготовку. Если время ограничено — Б.

### 8.3. Сколько кластеров деградирует (spec 8.20)

**Контекст.** Round-robin отправляет в каждый кластер долю 1/N размещений. При
одном деградировавшем кластере ожидается, что ошибки `naive` падают примерно
как 1/N, абсолютное преимущество `meta` сужается, а относительное снижение
может сохраниться. Манифест `experiments/chaos/netem-backend.yaml` и раннер
сценария 2 рассчитаны на один целевой кластер.

**Варианты.**

- **А. Один кластер при любом N.** Прямое продолжение сценария 2, раннер почти
  не меняется.
- **Б. Доля кластеров**, например ⌊N/2⌋. Ближе к региональному сбою, но нужны
  несколько NetworkChaos и правка раннера и сводки.
- **В. А для всех N плюс Б дополнительной серией при N = 5.**

**Рекомендация:** А как основная серия; В, если останется время.

**Ответ:**

### 8.4. Атрибуты новых кластеров (spec 8.21)

**Контекст.** `stand/clusters.yaml` — единственный источник атрибутов
(ADR 0009). Workload'ы потока сценария 2 без аннотаций `require-*`: при любой
разметке допустимы все кластеры. Разметка важна для сценария 3 и для
`/clusters/eligible`.

**Варианты.**

- **А. Нейтральная разметка:** регионы eu-west/eu-central попеременно,
  сертификации как у cluster-b. Сценарий 2 от неё не зависит, сценарий 3 не
  перепрогоняется.
- **Б. Разнообразная разметка**, чтобы множества допустимых кластеров у
  разных требований различались. Минус: смысл появляется только с
  требованиями в потоке, а это уже другой сценарий.

**Рекомендация:** А.

**Ответ:**

### 8.5. Какие сценарии гонять (spec 8.22)

**Контекст.** От N в первую очередь зависит сценарий 2. В сценарии 1 при
номинальных весах 1/N потерянные запросы до failover предсказуемо масштабируются
как 1/N, а panic-режим DR (ADR 0028) не затрагивается. Сценарий 3 от N не
зависит.

**Варианты.**

- **А. Только сценарий 2.**
- **Б. Сценарии 2 и 1:** +~1.5 ч на каждое N, проверяются веса 1/N и цикл DR
  на N кластерах.
- **В. Все три.**

**Рекомендация:** А. Сценарий 1 — только проверочным прогоном на N = 5, без серии.

**Ответ:**

### 8.6. Гипотезы и цена контура (spec 8.23)

**Контекст.** По правилу ADR 0035 гипотезы и критерии фиксируются до прогонов.
Кроме эффекта планировщика, с ростом N растёт нагрузка на сам контур: опрос
каталога (30 с), цикл DR (10 с), fan-out Thanos Querier, время решения
планировщика. У DR есть `dr_cycle_duration_seconds`. Есть ли метрики длительности
опроса каталога и решения планировщика, нужно проверить. Если их нет, добавить
вместе с серией (правило «механизм вместе со способом замера»).

**Варианты (не взаимоисключающие).**

- **H6.** Относительное снижение error rate `meta` против `naive` остаётся
  ≥ 20% при каждом N.
- **H7.** Абсолютная разница `ER_naive − ER_meta` убывает примерно как 1/N.
- **H8.** Длительность циклов контура растёт не быстрее линейно по N и при
  N = 5 остаётся меньше своего периода: цикл DR < 10 с, опрос каталога < 30 с.

**Рекомендация:** зафиксировать H6–H8 в ADR до первого прогона на VM. Численные
пороги H7 выбрать до прогонов.

### 8.7. Сравнимость: где снимать N = 2 (spec 8.24)

**Контекст.** TTD, p95 и поведение netem зависят от CPU и хоста. Текущие серии

**Варианты.**

  эффект N смешан с эффектом хоста.
