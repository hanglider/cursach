# Spec: сквозной контур управления надёжностью и размещением в федерации Kubernetes

> Развёрнутая постановка задачи, обоснование архитектурных решений и план
> реализации. Соответствует этапу 2 НИР.

> Принятые решения с обоснованием — в `docs/decisions/`.

## 1. Постановка задачи

### 1.1. Объект исследования

Федерация Kubernetes — набор из двух и более кластеров, управляемых совместно
через общую control plane. Каждый кластер владеет собственными ресурсами
(узлы, сеть, хранилище), может располагаться в другом регионе или у другого
провайдера, и **работает автономно при недоступности управляющей плоскости**.

Последнее свойство — не деталь, а ограничение на всю архитектуру: ни один
компонент контура не вправе предполагать, что управляющая плоскость всегда
доступна.

Рассматривается стенд из 2–3 кластеров с единой управляющей плоскостью.
Объект исследования — механизмы, обеспечивающие:

| № | Свойство |
|---|---|
| а | Измеримость надёжности через SLI/SLO |
| б | Устойчивость к типовым отказам |
| в | Автоматическое восстановление по DR-процедурам |
| г | Соблюдение политик размещения |
| д | Осмысленный выбор кластера планировщиком |

### 1.2. Исследовательские вопросы

**RQ1.** Как корректно определить и измерить SLI/SLO для мультикластерного
сервиса, агрегируя метрики из нескольких независимых кластеров?

**RQ2.** Какие конкретные механизмы (HPA, трафик-шейпинг, failover) в
наибольшей мере улучшают SLO при типовых сбоях — узел недоступен, сеть
деградирует, кластер частично отказывает?

**RQ3.** Как обеспечить воспроизводимый DR-цикл (обнаружение → автоматический
failover → управляемый подъём кластера) с фиксируемыми RTO и RPO?

**RQ4.** Как формализовать политики размещения workloads — ограничения по
регионам, меткам безопасности, доступности ресурсов — и обеспечить их
machine-readable исполнение без ручного вмешательства?

**RQ5.** Как построить meta-scheduler, агрегирующий метрики качества и
политики из каталога, и сравнить его эффективность с наивным (round-robin или
random) выбором кластера?

RQ5 — центральный. RQ1–RQ4 создают данные и условия, при которых на него можно
ответить количественно.

### 1.3. Целевые показатели

Работа считается выполненной при достижении следующих значений:

| Область | Метрика | Целевое значение |
|---|---|---|
| SLO / Observability | Доля успешных запросов (availability) | ≥ 99.0% в штатном режиме |
| SLO / Observability | p95 latency | < 200 мс при нормальной нагрузке |
| SLO / Observability | Error budget burn rate | Отслеживается, алерт при превышении |
| DR | Время обнаружения сбоя (TTD) | < 60 секунд |
| DR | Время восстановления (RTO) | < 5 минут для failover-сценария |
| DR | Потенциальная потеря данных (RPO) | < 30 секунд при stateless-нагрузке |
| Политики | Число нарушений политик размещения | 0 после внедрения enforcement |
| Meta-scheduler | Снижение error rate vs наивный выбор | ≥ 20% в сценарии деградации |

Все значения измеряются на стенде, в описанных ниже сценариях, и фиксируются
в машиночитаемом виде для последующего сравнения.

## 2. Анализ существующих решений

Раздел объясняет, **почему компоненты контура пишутся, а не берутся готовыми**.
Каждый инструмент ниже решает свою подзадачу корректно; проблема в стыках
между ними.

### 2.1. Управление федерацией

| Решение | Что даёт | Ограничение для этой задачи |
|---|---|---|
| **KubeFed v2** | Propagation ресурсов (Deployment, Service, ConfigMap) между кластерами через `FederatedResource` CRD | Сложен в эксплуатации; нет механизма принятия решений на основе метрик; активная разработка фактически заморожена с 2022 |
| **Admiralty** | Мультикластерное планирование через virtual-kubelet, прозрачное размещение подов в удалённых кластерах | Не решает policy enforcement; нет интеграции с SRE-метриками для принятия решений |
| **Liqo** | Расширение кластера ресурсами соседнего через peering | Хорош для burst-сценариев; нет детального контроля политик и DR-автоматизации |
| **OCM** (Open Cluster Management) | Placement API — декларативный выбор кластеров по меткам и ограничениям | Наиболее функциональное из существующих, но SLO-метрики не встроены в алгоритм выбора; значительный операционный overhead |

### 2.2. Наблюдаемость и SLO

**Prometheus + Grafana** — де-факто стандарт. Pull-модель с service discovery в
k8s. Для SLO существуют Pyrra и Sloth: генерируют recording rules и alert rules
из декларативных SLO-определений.

Ключевое ограничение в контексте федерации: **у каждого кластера свой
Prometheus**. Агрегация требует либо Prometheus Federation, либо
Thanos / Cortex / Mimir.

**OpenTelemetry** — CNCF-стандарт для трассировки, метрик и логов. Унифицирует
инструментирование независимо от бэкенда. Необходим для end-to-end латентности
запросов, проходящих через несколько кластеров: без сквозного трейса
мультикластерная латентность не разложима на составляющие.

**Thanos / Cortex / Mimir** — долгосрочное хранение и глобальный запрос к
метрикам нескольких Prometheus-инстансов. Thanos использует sidecar-компоненты
и object storage, что позволяет строить глобальный SLO-дашборд поверх данных
всей федерации.

### 2.3. Disaster Recovery

**Velero** — резервное копирование и восстановление состояния кластера (etcd +
Persistent Volumes через CSI), включая восстановление в другой кластер.
Ограничение: не автоматизирует failover трафика и не принимает решений на
основе метрик.

**Chaos Mesh / LitmusChaos** — контролируемое внесение сбоев: завершение подов,
сетевые задержки, отказы узлов. Обязательный компонент: без воспроизводимого
внесения отказа сравнение «до/после» не имеет силы.

**Argo Rollouts / Flagger** — прогрессивная доставка (canary, blue-green) и
автоматический rollback при деградации метрик. Решают задачу частично: работают
в границах одного кластера, не оперируют мультикластерным переключением
трафика.

### 2.4. Policy Enforcement

**Kyverno** — Kubernetes-native движок политик как admission webhook. Политики
на YAML, могут запрещать создание ресурсов, мутировать их или генерировать
связанные. Хорошо ложится на GitOps.

**OPA Gatekeeper** — admission webhook на базе OPA с языком Rego. Гибче и
выразительнее Kyverno, но требует знания Rego. Подходит для сложных политик с
условиями от внешних данных.

### 2.5. Планирование нагрузки

Стандартный `kube-scheduler` принимает решения только внутри одного кластера.
Для мультикластерного планирования существуют:

- **OCM Placement API** — декларативный выбор по меткам и ресурсным ограничениям
- **KEDA / Scheduled Scaler** — масштабирование по внешним метрикам
- **Custom controllers** (operator pattern) на базе `controller-runtime`

**Общий недостаток всех перечисленных:** ни одно решение не объединяет в едином
контуре политики размещения, актуальные SLO-метрики всех кластеров и DR-статус
кластера для принятия комплексного решения.

## 3. Узкие места

Пять выявленных проблем. Каждая напрямую отображается в компонент решения
(раздел 4).

### 3.1. Разрозненность компонентов

Prometheus знает метрики. Velero делает backup. Kyverno проверяет политики.
Admiralty планирует. Единого контура, где решение о размещении принимается с
учётом всей совокупности данных, не существует.

**Следствие:** оператор вручную координирует несколько систем — источник ошибок
и задержек при реагировании на инцидент.

### 3.2. Отсутствие метрико-ориентированного выбора кластера

Существующие federation schedulers (OCM Placement, Admiralty) решают на основе
**статических** атрибутов: метки, ресурсная ёмкость. Динамика не учитывается:
текущий error rate, p99 латентность, наличие активного инцидента.

**Следствие:** нагрузка направляется в деградирующий кластер до тех пор, пока
оператор не вмешается вручную.

### 3.3. Ручная и непроверяемая DR-процедура

Практики DR описаны в runbook'ах текстом, а не выполняются кодом. Velero
покрывает backup/restore состояния, но не полный цикл: обнаружение деградации →
переключение трафика → уведомление → восстановление исходного кластера →
возврат трафика.

**Следствие:** время восстановления определяется квалификацией и доступностью
дежурного инженера, а не свойствами системы.

### 3.4. Policy enforcement ограничен одним кластером

Kyverno и Gatekeeper — admission webhooks внутри кластера. Они не знают о
существовании соседних. Политика вида «этот workload размещается только в
кластерах с сертификацией PCI-DSS» невыразима без custom-логики: у webhook'а
нет данных о сертификациях других площадок.

### 3.5. Отсутствие федеративного каталога ресурсов

Meta-scheduler'у нужен актуальный инвентарь: метаданные кластеров,
сертификации, доступные ресурсы, SLO-статус. Ни одно из рассмотренных решений
не предоставляет структурированного API-доступного каталога с проверками
доверия.

## 4. Архитектура решения

### 4.1. Контур управления

```
Наблюдаемость → SLO Engine → Каталог кластеров → Meta-Scheduler → DR Controller
```

Каждый компонент — источник данных для следующего. Замкнутость контура
позволяет реагировать на изменение состояния инфраструктуры без ручного
вмешательства.

Соответствие узких мест компонентам:

| Узкое место | Компонент |
|---|---|
| 3.1 Разрозненность | Контур целиком |
| 3.2 Нет метрико-ориентированного выбора | Meta-Scheduler (§4.5) |
| 3.3 Ручной DR | DR Controller (§4.6) |
| 3.4 Политики в границах кластера | Двухуровневые политики (§4.4) |
| 3.5 Нет каталога | Registry Service (§4.3) |

### 4.2. Унифицированный слой наблюдаемости

Каждый кластер оснащается **Prometheus + OpenTelemetry Collector**. Агрегация
на уровне федерации — через **Thanos Querier** с sidecar-компонентами в каждом
кластере: это даёт единый endpoint для глобальных PromQL-запросов.

**Глобальные метрики.** Агрегированный SLO вида:

```
availability_global = sum(successful_requests) / sum(total_requests)
```

по всем кластерам федерации.

**Локальные SLI** — вычисляются для каждого кластера отдельно и являются
входными данными meta-scheduler'а:

- error rate
- p95 / p99 latency
- saturation (CPU / Memory utilization)

### 4.3. Федеративный каталог (Registry Service)

REST API-сервис на **FastAPI + PostgreSQL**, реестр кластеров федерации.

**Атрибуты регистрации кластера:**

| Поле | Описание |
|---|---|
| `id` | Идентификатор кластера |
| `region` | Регион размещения |
| `provider` | Провайдер |
| `labels` | Произвольные метки |
| `certifications` | Список: PCI-DSS, ISO 27001, GDPR-compliant |
| `slo_status` | `healthy` / `degraded` / `down` |
| `capacity` | Доступная ресурсная ёмкость |

**Обновление статуса:** каталог опрашивает Thanos Querier раз в **30 секунд**
и обновляет `slo_status` кластеров. Это обеспечивает актуальность данных для
meta-scheduler'а.

**Audit log:** каталог фиксирует принятые решения о размещении (§4.5, шаг 5) и
зарегистрированные нарушения политик (§6, сценарий 3).

### 4.4. Исполняемые политики размещения

Политики формализуются на двух уровнях.

**Уровень 1 — Hard constraints** (обязательные, нарушение недопустимо):

- Географические: workload X размещается только в кластерах с `region=eu-west`
- По сертификациям: workload X требует кластер с `certification=PCI-DSS`
- По ресурсам: минимум N CPU и M Gi памяти

**Уровень 2 — Soft constraints** (предпочтения, влияют на ранжирование):

- Предпочесть кластер с наименьшим error rate
- Предпочесть кластер с наименьшей p95 latency
- Предпочесть кластер, не затронутый активным инцидентом

**Механизм исполнения — двойной, и это существенно:**

| Уровень | Где исполняется | Как |
|---|---|---|
| Hard | Внутри кластера | Kyverno-политики, enforcement при попытке создания ресурса |
| Hard | На уровне федерации | Фильтрация кандидатов в meta-scheduler'е |
| Soft | На уровне федерации | Scoring-функция в meta-scheduler'е |

Kyverno здесь работает как backstop: даже если meta-scheduler ошибётся или его
обойдут, admission webhook отклонит некорректное размещение. Именно эта пара
даёт нулевое число нарушений из целевых показателей.

### 4.5. Meta-Scheduler

Контроллер на **Go + controller-runtime**, решающий, в какой кластер федерации
направить workload.

**Алгоритм:**

1. Получить список workloads, ожидающих размещения (Kubernetes watch API)
2. Для каждого workload извлечь из каталога список кластеров, прошедших
   фильтрацию по hard constraints
3. Для каждого допустимого кластера вычислить score:

   ```
   score = w1 * (1 - error_rate)
         + w2 * (1 / latency_p95)
         + w3 * (1 - saturation)
   ```

   где `w1`, `w2`, `w3` — настраиваемые веса
4. Выбрать кластер с максимальным score и создать в нём ресурс (Deployment / Job)
5. Зафиксировать решение в audit log каталога

**Наивный планировщик.** Реализуется параллельно: round-robin по доступным
кластерам. Оба варианта прогоняются на одних и тех же сценариях отказов,
метрики SLO сравниваются. Без наивной версии целевой показатель «снижение error
rate ≥ 20%» не имеет смысла.

### 4.6. DR-контроллер

Kubernetes-оператор (**Go + controller-runtime**), реализующий полный цикл.

**1. Мониторинг.** Периодический опрос Thanos/Prometheus по каждому кластеру.
Инцидент объявляется, если error rate превысил порог **или** кластер недоступен
дольше T секунд.

**2. Failover.** Уведомляет meta-scheduler о необходимости перенаправить новые
workloads в здоровые кластеры. Обновляет DNS/Ingress через ExternalDNS для
переключения трафика.

**3. Recovery.** После восстановления кластера выполняет smoke-тест (серия
тестовых запросов). При успехе — постепенный возврат трафика через traffic
shifting (Istio или аннотации Ingress).

**4. Документирование.** Записывает TTD, RTO, RPO в формате, пригодном для
последующего анализа.

## 6. Экспериментальные сценарии

Общий принцип для всех трёх: замер базовой линии → внесение отказа →
замер → сравнение. Отказ вносится через Chaos Mesh, то есть воспроизводимо.

### Сценарий 1: Отказ одного кластера

**Внесение:** принудительный вывод кластера из строя — отключение API-сервера
или всех подов.

**Измеряется:**
- TTD — время обнаружения DR-контроллером
- Failover time — время переключения трафика
- Итоговый SLO за период инцидента

**Сравнение:** с DR-контроллером vs без него.

### Сценарий 2: Деградация сети

**Внесение:** сетевая задержка **500 мс** и потери пакетов **10%** для одного
из кластеров.

**Измеряется:** реакция meta-scheduler'а — переключается ли он на здоровый
кластер и насколько быстро.

**Сравнение:** error rate и latency при умном vs наивном планировании.

Это ключевой сценарий для целевого показателя «снижение error rate ≥ 20%».

### Сценарий 3: Нарушение политики размещения

**Внесение:** попытка разместить workload с метками, нарушающими активную
Kyverno-политику — например, запуск на кластере без нужной сертификации.

**Измеряется:**
- Отклоняет ли система размещение
- Предлагает ли корректный кластер
- Фиксируется ли нарушение в audit log

## 7. Технологический стек

| Компонент | Технология | Обоснование |
|---|---|---|
| Кластеры (стенд) | kind / k3d | Лёгкий запуск на одной машине, подходит для экспериментов |
| Метрики | Prometheus + Thanos | CNCF-стандарт, поддержка федерации через Thanos |
| Визуализация | Grafana | Де-факто стандарт, готовые дашборды для k8s |
| Трассировка | OpenTelemetry + Jaeger | Vendor-neutral, CNCF, поддержка Go и Python |
| Chaos Engineering | Chaos Mesh | CNCF-проект, k8s-native сценарии |
| Policy Enforcement | Kyverno | YAML-native, не требует Rego — проще для старта |
| Каталог | FastAPI + PostgreSQL | Лёгкий REST API, надёжная СУБД, простой деплой в k8s |
| Meta-Scheduler | Go + controller-runtime | Официальный SDK для k8s-операторов |
| DR-автоматизация | Go + controller-runtime | Единый язык для всех контроллеров |
| Traffic switching | Ingress-nginx + ExternalDNS | Доступен в kind/k3d, достаточен для стенда |

**Языки:** Go для всего, что работает как контроллер внутри Kubernetes;
Python (FastAPI) для каталога как внешнего сервиса.

## 8. Открытые вопросы и требующее уточнения

Пункты ниже выявлены при формализации спецификации и требуют решения до начала
соответствующих задач. По мере принятия решений они переезжают в
`docs/decisions/` и удаляются отсюда.

### 8.1. RPO для stateless-нагрузки

Целевой показатель задаёт RPO < 30 секунд «при stateless-нагрузке». У
stateless-сервиса по определению нет персистентного состояния, которое можно
потерять. Требуется либо переопределить, что именно измеряется (потеря
in-flight запросов? состояние в кэше?), либо ввести stateful-компонент в
тестовый сервис, либо снять показатель.

**Блокирует:** задачу 7, замер RPO в сценарии 1.

### 8.2. HPA в списке исследуемых механизмов

RQ2 упоминает Horizontal Pod Autoscaler наряду с трафик-шейпингом и failover,
но HPA не фигурирует ни в архитектуре (§4), ни в плане реализации (§5), ни в
стеке (§7). Требуется решить: включать HPA в эксперименты или сузить
формулировку RQ2.

**Блокирует:** ответ на RQ2.

### 8.3. Веса scoring-функции

`w1`, `w2`, `w3` заявлены как настраиваемые, но способ их подбора не определён.
Варианты: фиксированные значения из здравого смысла, подбор по сетке на
исторических данных, sensitivity-анализ как отдельный результат работы.
Последний вариант выглядит наиболее ценным научно.

Отдельно: слагаемое `w2 * (1 / latency_p95)` не нормировано и при малых
значениях латентности доминирует над остальными. Требуется нормализация всех
трёх слагаемых к сопоставимой шкале.

**Блокирует:** задачу 6.

### 8.4. Порог и гистерезис объявления инцидента

DR-контроллер объявляет инцидент при превышении порога error rate или
недоступности дольше T секунд. Ни порог, ни T не заданы. Дополнительно:
не определён механизм защиты от флаппинга — колебание метрики вокруг порога
приведёт к циклу failover/recovery.

**Блокирует:** задачу 7, TTD в сценарии 1.

### 8.5. Взаимодействие DR-контроллера и meta-scheduler'а

§4.6 говорит, что DR-контроллер «уведомляет meta-scheduler». Протокол
уведомления не определён: через каталог (обновление `slo_status`), напрямую по
API, через Kubernetes-ресурс? Наиболее согласованный с архитектурой вариант —
через каталог, поскольку он уже является единственным источником состояния
для планировщика.

**Блокирует:** задачи 6 и 7 на стыке.

### 8.6. Судьба уже размещённых workloads при failover

Meta-scheduler описан как планировщик **новых** размещений (watch API →
размещение). DR-сценарий предполагает переключение трафика через DNS/Ingress.
Не определено, происходит ли перепланирование уже работающих workloads из
отказавшего кластера, или трафик просто уходит на существующие реплики в
здоровых кластерах. От ответа зависит смысл RTO.

**Блокирует:** задачу 7, интерпретацию RTO.

### 8.7. Object storage для Thanos на стенде

Thanos sidecar требует object storage. На локальном стенде (kind/k3d) это
дополнительный компонент — MinIO или аналог, — не упомянутый в стеке.

**Блокирует:** задачу 2.

### 8.8. Нагрузка и тестовый сервис

«Простой тестовый сервис» и «нормальная нагрузка» из целевых показателей не
специфицированы. Для воспроизводимости требуется зафиксировать: что за сервис,
какой генератор нагрузки (k6, Locust, vegeta), какой профиль RPS.

**Блокирует:** задачу 1 и все замеры.
