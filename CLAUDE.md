# НИР: сквозной контур управления надёжностью федерации Kubernetes

Исследовательский проект. Строим и измеряем контур:
`Наблюдаемость → SLO → Политики → Выбор кластера → DR-готовность`
на стенде из 2–3 kind-кластеров.

**Цель работы — не работающая система, а измеренный результат.** Механизм без
замера «до/после» ценности не имеет.

## Документация

Читай перед планированием любой задачи, в этом порядке:

- @docs/vision.md — зачем, границы работы, что явно вне задачи
- @docs/spec.md — постановка, целевые показатели, план по неделям, открытые вопросы
- @docs/architecture.md — компоненты, контракты, схема данных, инварианты
- `docs/decisions/` — принятые решения (ADR). Ищи здесь, прежде чем предлагать
  альтернативу: возможно, она уже рассмотрена и отклонена

Разделы, помеченные `[предложение]` в architecture.md, ещё не утверждены.
Если задача их затрагивает — спроси, не считай решёнными.

Раздел 8 spec.md — открытые вопросы. Пункты 8.1, 8.2, 8.6 блокирующие:
пока они не закрыты, соответствующие задачи не начинаем.

## Структура

```
docs/         документация проекта
tasks/        декомпозиция: backlog.md + NN-<slug>.md на задачу
stand/        развёртывание стенда (kind, observability, policies)
registry/     каталог кластеров, Python + FastAPI + PostgreSQL
scheduler/    meta-scheduler и наивный, Go + controller-runtime
dr-controller/ DR-оператор, Go + controller-runtime
experiments/  chaos-манифесты, k6-сценарии, results/ (коммитятся)
analysis/     обработка результатов, графики
```

## Команды

Проект на старте, часть команд ещё не существует — создавай по мере
реализации соответствующего компонента, не выдумывай их наличие.

```bash
make stand-up        # поднять 4 kind-кластера (control + федерация)
make stand-down      # снести стенд
make lint            # линт всего проекта
make test            # тесты
```

Go-модули: `go test ./...`, `go vet ./...` в `scheduler/` и `dr-controller/`.
Python: `pytest`, `ruff check` в `registry/`.

## Правила

**Инварианты.** Нарушение любого — дефект, а не компромисс. Полный список в
architecture.md §9, самые важные:

1. Компоненты контура живут **вне** федерации. Наблюдатель не размещается в
   наблюдаемом — иначе сценарий отказа кластера непроверяем.
2. Meta-scheduler читает состояние **только из каталога**, не из Prometheus
   напрямую.
3. Оба планировщика (умный и наивный) соблюдают hard constraints. Разница
   между ними строго в учёте динамических метрик.
4. Каждое решение о размещении пишется в `placement_decisions` со **всеми**
   кандидатами и скорами, не только с победителем.
5. `unknown` (метрики недоступны) ≠ `down` (кластер мёртв). Не смешивать:
   смешение даёт ложный failover.
6. Время внесения отказа берётся из Chaos Mesh, не из наблюдений контура.

**Воспроизводимость.** Всё разворачивается с нуля из репозитория. Ручной шаг,
не описанный в `stand/`, — не сделанная работа.

**Замеры.** Любой механизм реализуется вместе со способом измерить его эффект.
Если непонятно, чем мерить, — сначала это, потом код.

## Чего не делать

- **Не менять целевые показатели spec.md** без явного согласования. Это
  критерии приёмки работы, а не ориентиры.
- **Не расширять область.** Границы в vision.md §«Границы работы» жёсткие:
  не production-ready, не реальные облака, не stateful-репликация, не
  оптимизация стоимости.
- **Не трогать `experiments/results/`** — сырые данные прогонов, основной
  результат НИР.
- **Не удалять и не пересоздавать кластеры** (`kind delete`, `kubectl delete
  ns`) — только вручную, скажи мне.
- **Не коммитить** kubeconfig, токены, содержимое `.env`.
- **Не подменять baseline.** Наивный планировщик — часть научного результата,
  его нельзя «улучшать».

## Рабочий процесс

Задачи лежат в `tasks/`, соответствуют плану из spec.md §5.

Перед реализацией:

1. Прочитай задачу в `tasks/NN-*.md` и разделы spec/architecture, которых она
   касается
2. Если в них есть неоднозначность или противоречие — **спроси, не
   додумывай**. Молча выбранная интерпретация дороже вопроса.
3. Предложи план, дождись подтверждения
4. Реализуй, обнови статус задачи

Принятое архитектурное решение оформляется как ADR в `docs/decisions/`:
`NNNN-slug.md`, секции Статус / Контекст / Решение / Последствия.
Секция «Последствия» обязана содержать минусы принятого варианта.

Если по ходу работы выясняется, что документ неверен, — правь документ, не
обходи его в коде. Расхождение кода и документации хуже, чем ошибка в
документации.
